P0 — 阻断问题

P0-1下载链路未注入后端认证头，飞牛后端的下载必失败
backend/download/SongDownloadManager.kt（构造参数 client） · StreamUrlResolver.kt

飞牛是第一个需要 Authorization: <userToken> 请求头的后端。播放链路（ExoPlayer / Coil）通过 BaiduHttpDataSourceFactory 拦截器 + BackendAuthHeaders.forHost(host) 注入了认证头（F-2 修复），但下载链路使用独立自建的 OkHttpClient，没有任何拦截器——downloadFile() 与 headContentLength() 的请求对飞牛 track/stream 端点必然 401，重试 3 次后失败。同链路的 HQ 人声分离下载（HqSeparationOrchestrator.resolveInputPath）也是独立裸 client，同样 401。

private val client: OkHttpClient = OkHttpClient.Builder()
    .connectTimeout(15, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .build()   // ← 无拦截器，飞牛流地址 401
给下载 client 添加与播放链路相同的 host 精确匹配拦截器（复用 BackendAuthHeaders.forHost），或在 NasMusicApp 构造共享的"下载用 OkHttpClient"注入。
P0-2recoverAfterCrash 孤儿恢复分支永不命中，上次修复无效
backend/download/SongDownloadManager.kt（recoverAfterCrash 分支 2） · DownloadRepository.newDownloadingEntity

// newDownloadingEntity: audioPath = null, tmpPath = tmpPath, status = DOWNLOADING
// recoverAfterCrash:
val finalPath = entity.audioPath   // 恒为 null → 分支永不命中
DOWNLOADING 记录增加 finalPath 字段（构建路径时已知），或恢复时用 paths.buildFinalPath(song) 反推。

P1-4空间预估公式单位错 1000 倍
SongDownloadManager.estimateFromSong · AutoDownloadController.estimateFromSong

durationMs / 1000 * bitrate / 8 中 bitrate 是 kbps，结果单位是 KB 却按字节比较——160kbps×240s÷8=4800 被当 4.8KB，预检形同虚设。缓解：下载中有 hasRoomFor(0) 复查与 Content-Length 校验兜底不会写爆磁盘，但前置提示与 AutoDownload 空间判断失效。

结果 ×1024 补单位。
P1-5cancelAll 重启 loop 造成新旧 loop 并存，破坏串行队列保证
backend/download/SongDownloadManager.kt:432-450（cancelAll） · :111-114（loop 启动）

定性修正（2026-09-16 复核）：原描述"与新入队存在竞态窗口"不够精确。真正的缺陷在 cancelAll 末尾的 startLoop()——先 currentDownloadJob?.cancel() 再立即重启，而旧 loop 此刻通常阻塞在 OkHttp 的 socket 读上（协程 cancel 是协作式的、不中断阻塞 IO），旧 loop 未退出、新 loop 已开始消费 → 两个 executeDownload 短暂并存，破坏"串行队列只有一个消费者"的保证（两个 .part 并发写、currentCall 互相覆盖）。原先担心的"enqueue 落在标记 FAILED 与 startLoop 之间被误杀"只是同一处代码的次要表现。

改为 call.cancel()（中断阻塞读）+ cancelRequested 标志（进行中任务直接落 FAILED、不再重试）+ drain 两条排队队列；loop 常驻唯一实例、不再重启。

本轮处置：已按此实现（工作区已改、未提交）——SongDownloadManager.kt:100-101,111-114,188-193,432-450。

P1-6SAF 增量导出判定失效，shouldOverwrite 对 SAF 恒真
backend/export/SongExporter.kt:222-227, 313-319

shouldOverwrite 里 targetFile 仅在 ExportRoot.File 分支返回非 null，SAF 分支恒 null → shouldOverwrite 恒 true，SAF 路径只剩 export_records 过滤。清掉导出记录后重导，SAF 目标上同名不同长文件被无条件覆盖。

SAF 分支用 resolveChildDoc 反查目标 DocumentFile 长度对比。
P1-7next() REPEAT_ONE / 队尾 REPEAT_ALL 分支绕过 T3 三元组同帧发布
player/PlayerManager.kt:774-796 · onPlaybackEnded

REPEAT_ONE 分支只 update currentIndex 不更新 currentSong，依赖 onMediaItemTransition 补齐——队列快照与 ExoPlayer 内部队列短暂不一致时 UI 读到"新索引 + 旧歌名"中间态。onPlaybackEnded 的 REPEAT_ALL 用 playQueue(queue, 0) 整队重放，queue 已被改动时会回滚用户操作。

update 中同时写 currentSong；REPEAT_ALL 重放改 seekTo(0)。
P1-8RemoteControlServer /api/queue/add 反序列化不可信 JSON 直接入队
net/RemoteControlServer.kt:170-176

手机提交的任意 JSON 直接 gson.fromJson 成 Song 后入队，无字段校验。Song 含 streamUrl/path——LAN 内任何设备可注入任意 URI。服务器绑定 0.0.0.0，其余端点都做了 index 边界校验，唯独此端点无。

校验必填字段与 URI scheme 白名单（http/https/content/file）。
P1-9BackupTransferServer 上传路径的内存安全待确认 —— 已核验为误报，撤回
net/BackupTransferServer.kt:343-397（handleUpload）

核验结论（2026-09-16）：误报，撤回。handleUpload 并未使用 parseBody（注释明确说明为规避部分 ROM 的 Charset.defaultCharset() 非 UTF-8 才改为直读 inputStream）。它先按 content-length 预检（:348-356，>MAX_UPLOAD_BYTES 直接拒绝），再以 16KB 分块累积读取、totalRead > MAX_UPLOAD_BYTES 时立即中止（:359-371）——上限判定发生在读入过程中而非之后；且刻意不按 Content-Length 预分配数组（防客户端谎报导致巨型 ByteArray OOM）。内存安全已达标，无需修复。

此条目留档防止后续审查重复上报。

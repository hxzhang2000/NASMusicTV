## 二、硬伤（必须修复）

### #1 设备码请求端点写错（API 事实错误）

§3.1 流程第 1 步与 §6.1.2 注释写：

```
GET https://openapi.baidu.com/oauth/2.0/token?grant_type=device_code&client_id&client_secret&scope=basic,netdisk
```

实际端点（官方文档 + baidu-netdisk-sdk(Rust) + 社区多方一致）：

```
GET https://openapi.baidu.com/oauth/2.0/device/code?response_type=device_code&client_id={APP_KEY}&scope=basic,netdisk
```

三处不同：**端点是 `/oauth/2.0/device/code` 不是 `/oauth/2.0/token`**；参数名是 `response_type=device_code` 不是 `grant_type=device_code`；请求设备码**不需要 client_secret**（轮询换 token 时才需要 client_id + client_secret）。方案中的轮询端点（`token?grant_type=device_token&code={device_code}`）是对的。若照方案实现，第 1 步就会失败，整个 TV 首选鉴权流程跑不通。

### #2 dlink 缓存 TTL 全文自相矛盾

§11 问题 6 已"确认保持 5 分钟、不单独放宽"，但正文五处仍是 7h 旧稿：

- §2.1："建议为百度源单独放宽缓存 TTL"
- §3.4 对策表："缓存 TTL 设为 7h（留余量）"
- §6.3.1 代码注释："缓存 TTL 设 7h"
- §6.3.2 注释："7h 缓存……放宽 TTL"
- §9 风险表："resolvePlayUrl 缓存 TTL 7h"

评审结论未回填正文。且从代码看 `CachedPlayUrl` 无按源区分 TTL 的结构，Q6 的"零改动"选择与代码事实一致——7h 表述应全部删除。**注意**：TTL=5min 意味着 dlink 有效期（小时级）远大于缓存，方向安全；但 §9 "dlink 8h 过期→播放失败清缓存重解析"的兜底逻辑仍需保留（长时间播放同一队列中间切歌回来时）。

### #3 搜索参数 key/word 自相矛盾

§3.2 用 BoxPlayer 实证明确纠正"**search 参数是 `key` 不是 `word`**"，但：

- §6.2.1 模式表仍写 `method=search&word={kw}&category=2`
- §6.2.2 代码 `searchAudio(word: String, ...)` 参数名沿用 word

正文结论与设计章节脱节，实施者容易照抄错参数。

### #4 BaiduPanApi 的 API_BASE 与 §3.2 结论冲突

§3.2 明确"列表/搜索走 `/xpan/file`，元数据/dlink 走 `/xpan/multimedia`，两者 base 不同勿混用"，但 §6.2.2 代码只有一个 `API_BASE = ".../xpan/multimedia"`。照此实现 list/search 会打错端点。需要两个 base 常量（FILE_BASE / MULTIMEDIA_BASE）。

### #5 §3.1 编辑残留（结构损坏）

第 232 行"Token 存储"段之后：

- 233-237 行是一段悬空的授权码模式 URL 参数碎片（`&redirect_uri=oob...&display=tv&qrcode=1...`）
- 239-264 行出现没有第 1 步的"2. 3. 4."授权码流程步骤
- 266 行又重复一遍"Token 存储"段

明显是设备码模式替换授权码模式重写时的残留，必须整段删除（备选方案的授权码流程在 §6.1.2 `buildAuthUrl` 处已有正确保留）。

### #6 §6.5.3 代码块复制粘贴事故

1259-1264 行，`searchMv` 的收尾部分重复出现两次（`return@withContext buildResult(...)` + `null // 未命中` 注释 ×2）。该代码无法编译。

### #7 §3.2 表格行重复断裂

287 行注意事项之后，288 行孤立地重复了一行 `filemetas` 表行（与 285 行重复），表格结构断裂。

## 三、设计缺口（评审应决策）

### #8 BaiduMvFileService 拿不到歌曲上下文 —— 接口签名断层（最重要的设计问题）

现有 `MvSearchService.searchMv(title, artist, excludeBvids, minSimilarity)` **只传标题和艺术家**。但 §6.5.3 的实现需要：

1. 判断"仅对百度歌曲生效" → 需要 `song.networkSource`
2. `prefs.getBaiduSongPathByFsId(...)` 查歌曲 path（同目录同名匹配）→ 需要 `song.id` / fs_id

接口不传 Song，两个信息都拿不到。方案 Phase 6 步骤 30 说"searchMvFor 按 source 标签路由"，但**从未明确这需要改 `MvSearchService` 接口签名**（如 `searchMv(song: Song, ...)` 或新增带 Song 的重载），也未提 `BilibiliMvService` 的适配成本。建议：接口加默认参数 `searchMv(title, artist, excludeBvids, minSimilarity, song: Song? = null)`，Bilibili 不用改，Baidu 用 song 判源与查 path。

### #9 注册 "baidu" 进 services map 的副作用未评估

`NetworkMusicManager.search()` 按 `orderedServices()` 依次 fallback 调用**所有**注册源的 `svc.search(keyword)`。注册 baidu 后：

- Network Tab 普通关键词搜索也会打到百度（先查本地索引，未命中走百度 API）
- `availableSources()` 会把 "baidu" 暴露为默认源候选（设置页网络音乐源切换 UI）

前者可能是期望的"多源聚合"，但方案未提；若不希望，需在 `BaiduNetdiskService.search` 里处理或 manager 层过滤。后者可能需要在设置页过滤掉网盘类 sourceId。**建议方案补一节"注册副作用"明确决策。**

### #10 refresh_token 一次性语义未写明

官方文档明确：refresh_token **只支持使用一次**，使用后失效，下次刷新须用上次刷新响应中的新 refresh_token；刷新失败时旧 refresh_token 失效，需重新走完整授权。§6.1.2 `refreshAccessToken` 只写"更新 prefs 中的 token"，§3.4 提了并发刷新加锁（好）。应补充：**刷新成功必须原子性保存新 refresh_token**（半写状态会导致下次刷新失败→被迫重新设备码授权）；刷新失败直接降级为"重新登录"引导，不做循环重试。

### #11 索引构建策略二义：listall vs BFS

- §6.2.1 表格：全量索引用 `method=listall&recursion=1`（一次 API 递归拉全）
- §6.2.3：BFS 逐目录扫描 + 60ms 节流 + RateLimiter（BoxPlayer 实证模式，海量 list 调用）
- §4.1 待验证项又把 `listall` 端点列为"未验证"

两条是不同的实现路径（请求数、限流风险、进度上报粒度都不同）。Phase 2 步骤 10 "list/listall/search/filemetas 封装"两者都包，含糊。**建议定论：主路径 BFS（已验证），listall 作为已验证后的可选加速**，并据此修正 §6.2.1 表格与预估工时。

### #12 MvSearchManager 现有行为与方案的差异未完整交代

- 内存缓存 key 是 `title|artist`（`buildCacheKey`），非 song.id——方案未提；同名同歌手的 NAS 歌与百度歌共享 MV 结果（现状行为，语义可接受，但应写明）
- `MvSearchManager.resolveMv(bvid)` 轮询所有 service：B 站 service 会收到 `ntwk_baidu_mv_*` 前缀的 bvid（靠前缀不匹配自然失败返回 null，可接受，但值得在 §6.5.4 注明依赖"service 对未知 bvid 优雅返回 null"这一契约）
- 持久缓存命中路径 `persistentCache.get(song.id) → resolveMv(entry.bvid)`：百度歌曲存的是百度 bvid，路由依赖 service 顺序（Baidu 在前）——方案有交代（步骤 31），OK

### #13 索引缓存所有权不一致

§6.3.2 `BaiduNetdiskService.search` 从 `prefs.baiduFileIndexCache` 读索引；§6.2.3 索引归属 `BaiduFileIndexCache(context)`（filesDir JSON，独立类）。应统一为 **service 持有 cache 实例（构造注入），prefs 只存配置**，否则出现双源读写。

### #14 BaiduFileMeta 两处定义冲突

- §6.2.2 版：`dlink: String?`、`durationMs/durationSec` 双字段（毫秒优先）、`bitrate: Int?` —— 符合响应容错原则
- §7.1 版：`dlink: String`（非空）、`duration: Long`（仅秒）、`bitrate: Int`

应统一为 §6.2.2 宽松版。同类问题：`BaiduPanApi` §6.2.2 是 class、§7.3 是 interface，二选一。

1. **架构选型论证充分且与源码完全吻合**：百度走 `NetworkMusicService` 而非 `BackendAdapter` 的三条理由（dlink 时效/扁平结构/OAuth）均经代码核实，"零侵入主播放器"的收益真实存在

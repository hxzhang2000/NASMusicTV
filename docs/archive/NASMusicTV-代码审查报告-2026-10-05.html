2. 架构设计评估（分层）

2.1 后端适配层 —— 资源治理最扎实的一层

  • 5 个 NAS 适配器统一实现 BackendAdapter，由 BackendRegistry 手动 DI 管理；sharedConnectionPool（5 空闲 / 5min）+ sharedDispatcher（16/8 并发上限）+ 守护线程池跨适配器共享，并有「适配器 close 禁止 shutdown 共享池」的显式约束。
  • 凭据传递「URL query + Header」双轨且边界清晰：Jellyfin api_key / Subsonic u/p/t 走协议规范的 query；飞牛 Authorization: <userToken> 走请求头，经 host 精确匹配注入、302 不跨域泄漏。
  • 错误策略统一「catch → 空值 + AppLog」，健壮性优先；代价是静默失败与「正常空结果」不可区分（见 H1 相关、M9）。

2.2 播放层 —— 单一调度中心 + 刻意简单

  • PlayerManager 为全局唯一播放状态中枢，1s Handler 轮询驱动进度/状态，刻意不依赖 ExoPlayer 回调；release() 同步 removeCallbacks 收口，无 Handler 泄漏。
  • PlaybackService 只承担 Media3 会话、通知、URI 解析三件事，与 PlayerManager 职责边界清晰；网络歌曲 onNeedResolveStreamUrl 信号链与 MediaSessionAccessPolicy 纯函数安全边界均有测试锁定。

2.3 UI 层 —— 状态架构健康，文件结构是最大债务

  • StateFlow 单一真相源 + 手动 when 导航（约 15 分支）+ 三形态适配（TV / 手机竖屏 / 手机横屏）；UiMode.deriveUiMode 为可单测纯函数，derivedStateOf 使用位置正确。
  • MainViewModel（3434 行）是「事件路由器 + 域状态持有者」的巨型混合类，内部已委派 13 个子 VM、并以 ViewModelEvents 冻结事件契约 + constructorReady 门闩补结构——说明团队已意识到失控并用文档化手段在补，但文件级上仍是一个类做十件事（H2、M13）。
  • 两套并行的可聚焦组件体系（FocusableSurface 抽象 vs 列表 item 手写 onFocusChanged 样板）并存（M14）。

2.4 渲染层 —— 零分配纪律 + 门禁测试

  • 「零分配」以源码扫描门禁强制执行（PerfBudgetContractTest 正则锁定每帧可达原语），SeasideRenderer 全部绘制走预分配数组 + 复用的 NativePath + 合批原语。
  • 时钟统一：绘制路径 ctx.nowMs 恒等于 frame.timeMs，无墙钟/单调钟混用；帧循环由 Compose 组合销毁自动取消。
  • 音频→渲染耦合被刻意收窄为「外观参数」注入，SeasideWaves 类头硬约束零音频引用、零 Android import、确定性 hash——同类工程中罕见的纪律，单测 6 处负向自证（喂破实现必须失败）。

2.5 持久化层 —— 迁移策略边界明确

  • 三库取舍清晰：local_music.db v3 走破坏性迁移（可由重扫重建）、downloads.db v2 走显式迁移（用户数据禁止回退）、photo.db v1；AppPreferences 敏感键 AES-GCM + Delta 备份。
  • 下载状态机是设计中标注最密的部分（P1-x 编号注释 + 完整实现同步），但存在一处取消竞态（M4）。

### 2.1 存储现状全景（源码清点）

全项目**只有 1 个 Room 库**，其余持久化全部是 DataStore + Gson JSON / 裸文件。清点如下：

| # | 存储方式 | 载体 / 位置 | 存的内容 | 量级 | 是否可重建 |
|---|----------|-------------|----------|------|------------|
| A | **Room SQLite** | `local_music.db` v2（`backend/local/db/`） | `local_songs` 索引：18 字段，`path` 唯一索引 | 数千~数万行 | 可（重扫）但代价高 |
| B | DataStore **标量** | `nas_music_tv.preferences_pb`（`AppPreferences.kt:69-202`，约 40 个 key） | 服务器地址/token、主题、播放模式、缓存开关、歌词偏移、均衡器、语言… | 单值 | 否 |
| C | DataStore **+ Gson 字符串** | 同上文件，8 个 `stringPreferencesKey` | `recent_song_objects`、`play_counts`、`network_favorites`（上限 500）、`local_playlists`、`last_queue`、`play_records`、`search_history`（上限 200/30 天）、`cloud_drive_configs` | 中小列表 | 部分 |
| D | **JSON 文件**（`filesDir`） | `cover_url_cache.json`（上限 10000）、`lyrics_cache.json`（上限 2000）+ `lyrics_cache/{id}.lrc`、`mv_cache.json`、`baidu_index.json` | 封面 URL、歌词、MV、网盘索引 —— 全是**缓存** | 有上限 LRU | ✅ 是 |
| E | **二进制/文本文件**（`cacheDir`） | `album_covers/*.jpg`、`accompaniment/*.wav` | 提取的内嵌封面、伴奏分离产物 | MB 级 | ✅ 是 |
| F | **文件系统** | `getExternalFilesDir(null)/lyrics`、USB/SD | 下载的歌词、用户音乐 | GB 级 | ❌ 否 |

关键观察：

1. **数据库只用在"要查、要比对、量会涨"的地方** —— `local_songs` 之所以上 Room，是因为 `LocalMusicRepository.incrementalScan()` 每次启动要把扫描结果与全表做差集（:40-65）、`search()` 要走 `LIKE` 索引查询（:83-86）。这两件事 JSON 做不了：JSON 只能整表反序列化进内存再遍历。
2. **缓存类数据一律 JSON 文件** —— 封面 URL / 歌词 / MV 全部满足"整读整写 + 可重建 + 有 LRU 上限"三条件，用 JSON 成本最低，且便于备份导出（`exportAll()/importAll()` 是这一层类的统一接口）。
3. **`LyricsPersistentCache` 是正确范式** —— 索引 JSON 只存 metadata，`lrcText` 单独落 `lyrics_cache/{songId}.lrc`（:33-34、:69-73）。**大文本不进索引**，这条规则本方案的下载索引要照抄（歌词正文落 `.lrc` 文件，DB 只存路径）。
4. **项目没有"DataStore 存大列表"的包袱** —— C 类列表都有硬上限（500 / 200），并且 `AppPreferences` 在写入前主动 `copy(streamUrl = null)` 瘦身（:1338、:1343），说明作者清楚 DataStore 单 key 不宜膨胀。

### 2.2 选型决策规则（本方案遵循）

按序回答四个问题，第一个命中即定案：

| 判据 | 结论 | 本项目实例 |
|------|------|------------|
| ① 需要按字段查询 / 聚合（COUNT、SUM）/ 排序？ | **数据库** | 下载配额 COUNT、占用 SUM、按 `dedupeKey` 查重 |
| ② 条目会持续增长（> 数百）且需**局部更新**？ | **数据库** | 下载进度每 512KB 更新一次 |
| ③ 单值开关 / 配置标量？ | **DataStore** | 自动下载开关、数量上限 |
| ④ 整读整写、可重建、有 LRU 上限？ | **JSON 文件** | 封面 URL 缓存、歌词缓存 |
| ⑤ 体积大（图片/音频/文本正文）？ | **文件系统** | 歌曲、封面 jpg、歌词 lrc |

### 2.3 下载功能的落位结论

| 数据 | 落哪里 | 理由 |
|------|--------|------|
| 下载任务（状态、进度、路径、大小、dedupeKey、是否自动下载、时间戳） | **Room `downloads.db`** | 命中 ①（COUNT 配额 / SUM 占用 / 按 key 查重）+ ②（高频局部更新） |
| 自动下载开关、数量上限 | **DataStore 标量** | 命中 ③，与现有 `settings_cache_lyrics` 等并列 |
| 歌曲文件 `.mp3/.flac/.m4a` | **文件系统** `Music/<歌手>/<专辑>/` | 命中 ⑤，且是需求 2 的硬性要求 |
| 封面 `cover.jpg` / `artist.jpg` / 旁路的同名 `.jpg` | **文件系统** | 需求 3/4/5 硬性要求；URL 缓存可复用现有 `CoverUrlPersistentCache`（JSON） |
| 歌词正文 | **优先内嵌进音频文件**；不支持内嵌的格式落同名 `.lrc` 文件 | 需求 5；正文不入 DB（照抄 2.1 观察 3） |
| UI 实时进度 | **内存 `StateFlow`**，不落盘 | 进程内即可，落盘是无谓 IO |
| 导出记录（卷 ID、相对路径、源路径、大小、导出时间） | **Room `downloads.db` 新表 `export_records`** | 命中 ①（COUNT 进度 / 按 `volumeId+relPath` 查重实现增量）+ ②（逐首追加写入）。不进 DataStore：条目数=歌曲数×设备数，且需按卷查询 |
| SAF 授权 URI（treeUri） | **DataStore 字符串** | 命中 ③，单值标量；配合 `takePersistableUriPermission` 跨重启生效 |

**为什么不沿用项目的"DataStore + Gson 列表"写法**（即 `networkFavorites` 那一套）：

- **写放大**：JSON 列表每改一条就要序列化整表 + DataStore 全文件重写。500 条收藏约 200KB，改一首 = 重写 200KB；下载进度若走这条路，一首 8MB 的歌按 512KB 粒度要整表重写 ~16 次。
- **无索引**：`dedupeKey` 查重要全量反序列化后遍历，O(n) 且阻塞。
- **并发**：下载队列（后台协程）与 UI 查询同时读写，DataStore 是串行事务，会被进度更新反复打断。
- **损坏面**：整文件重写过程中断电/杀进程 → 半截 JSON。`CoverUrlPersistentCache.save()`（:103-110）目前就是直接 `file.writeText()` 非原子写，靠 `load()` 的 try/catch 兜底（缓存全丢但不崩）—— **这是现有代码的一处隐患，本方案新增的 JSON 必须"临时文件 + rename"原子替换**，不复制这个写法。

**反过来，数据库也不是万能的** —— 歌曲文件、封面、歌词正文一律不进 DB（BLOB 会让 DB 体积暴涨、备份与 VACUUM 代价高）。DB 只存**元信息 + 路径**。

### 3.2 单曲下载时序

```
点击 ⬇ / 自动触发
 →① isDownloadable(song)                     否 → 不显示/不触发
 →② StorageGuard.hasRoomFor(estimatedBytes)  否 → showError(空间不足) + 结束
 →③ StreamUrlResolver.resolve(song)          失败 → FAILED + 提示
 →④ DownloadPathBuilder.build(song, ext)    → {artistDir, albumDir, tmpFile, finalFile}
 →⑤ 下载到 Music/.tmp/<name>.part（每 512KB：进度回调 + 空间复检）
 →⑥ CoverFileWriter：artist.jpg / cover.jpg（不存在才写）
 →⑦ MediaTagWriter.embed()  成功=内嵌 / 失败=旁路 <name>.jpg + <name>.lrc
 →⑧ tmpFile 原子 rename → finalFile（跨目录同分区，OK）
 →⑨ DownloadRepository.upsert(COMPLETED, ...)
 →⑩ _downloadStates[key] = Completed；发 MediaStore 扫描（best-effort）
```

## 4. 存储目录设计

### 4.1 根目录（决策 D1）

| 方案 | 路径 | 权限 | 多级目录 | 其他播放器可见 | 卸载保留 | TV 兼容 | 结论 |
|------|------|------|----------|----------------|----------|---------|------|
| **A（推荐）** | `getExternalFilesDir(Environment.DIRECTORY_MUSIC)` | 免权限（API 19+） | ✅ | ❌（Android 11+ 文件管理器受限） | ❌ | ✅ | **默认** |
| B | `Music/NASMusicTV/...`（MediaStore） | API≤28 需 WRITE_EXTERNAL_STORAGE（已声明 maxSdk 28）；API 29+ 免权限 | ⚠️ API 29 仅一级子目录，多级需 API 30+ | ✅ | ✅ | ⚠️ | 备选 / 导出目标 |
| C | SAF 授权目录树 | 免权限，一次性授权 | ✅ | ✅ | ✅ | ⚠️ TV 可能无 DocumentsUI | P1 |

**空值兜底**：`getExternalFilesDir` 返回 null（极少数无外存设备）→ 回退 `context.filesDir/music`。

### 4.2 目录结构


### 4.3 命名与清洗（`DownloadPathBuilder`）

| 规则 | 说明 | 示例 |
|------|------|------|
| 主艺术家 | `ArtistSplitter.split(artist).firstOrNull()` 取主艺术家 | `周杰伦/杨瑞代` → `周杰伦` |
| 非法字符 | `[\/:*?"<>\|\x00-\x1F]` → `_` | `AC/DC` → `AC_DC` |
| 空白 | 连续空白折叠为单空格；首尾 trim；去掉结尾 `.` 与空格 | `Album. ` → `Album` |
| 长度 | 单段 ≤ 80 字符 | — |
| 空值 | 歌手→`未知歌手`；专辑→`单曲`；标题→`未命名` | — |
| 曲目号 | `trackNumber > 0` → `%02d - ` 前缀 | `01 - 七里香.mp3` |
| 冲突 | 已存在且非本索引记录 → ` (2)`、` (3)` | `七里香 (2).mp3` |
| 扩展名 | `Content-Type` / URL 路径推断，缺省按源类型，未知回退 `.mp3` | `audio/flac` → `.flac` |
| 编码 | 全程 UTF-8；源元数据乱码先过 `EncodingUtils.fixEncoding()` | 见 `AGENTS.md` GBK 坑 |

```kotlin
class DownloadPathBuilder(private val rootProvider: () -> File) {

    data class Paths(
        val artistDir: File,
        val albumDir: File,
        val baseName: String,   // 不含扩展名，旁路文件用
        val tmpFile: File,
        val finalFile: File
    )

    fun build(song: Song, ext: String): Paths {
        val root = rootProvider()
        val artist = sanitize(ArtistSplitter.split(song.artist).firstOrNull() ?: song.artist)
            .ifBlank { "未知歌手" }
        val album = sanitize(song.album).ifBlank { DEFAULT_ALBUM }
        val title = sanitize(song.title).ifBlank { "未命名" }

        val artistDir = File(root, artist)
        val albumDir = File(artistDir, album)
        val baseName = if (song.trackNumber > 0) "%02d - %s".format(song.trackNumber, title) else title
        val finalFile = uniqueFile(albumDir, baseName, ext)
        val tmpDir = File(root, TMP_DIR).apply { mkdirs() }
        val tmpFile = File(tmpDir, "${finalFile.name}.part")
        return Paths(artistDir, albumDir, finalFile.nameWithoutExtension, tmpFile, finalFile)
    }

    private fun uniqueFile(dir: File, base: String, ext: String): File {
        var candidate = File(dir, "$base.$ext")
        var i = 2
        while (candidate.exists()) { candidate = File(dir, "$base ($i).$ext"); i++ }
        return candidate
    }

    companion object {
        private val ILLEGAL = Regex("[\\\\/:*?\"<>|\\u0000-\\u001F]")
        private const val MAX_SEGMENT = 80
        const val TMP_DIR = ".tmp"
        const val DEFAULT_ALBUM = "单曲"

        fun sanitize(raw: String): String =
            ILLEGAL.replace(raw, "_")
                .replace(Regex("\\s+"), " ")
                .trim().trimEnd('.', ' ')
                .let { if (it.length > MAX_SEGMENT) it.take(MAX_SEGMENT).trimEnd() else it }
    }
}
```

### 5.1 状态机

```
  [None] ─enqueue─▶ PENDING ─▶ DOWNLOADING ─▶ TAGGING ─▶ COMPLETED(✓)
                       │           │              │
                       │           │              └─▶ COMPLETED(降级：已写旁路文件)
                       ▼           ▼
```

### 5.2 编排器（`SongDownloadManager`）

```kotlin
class SongDownloadManager(
    private val context: Context,
    private val scope: CoroutineScope,                 // NasMusicApp.applicationScope
    private val repo: DownloadRepository,
    private val storage: StorageGuard,
    private val paths: DownloadPathBuilder,
    private val resolver: StreamUrlResolver,
    private val tagWriter: MediaTagWriter,
    private val coverWriter: CoverFileWriter,
    private val lyricsProvider: suspend (Song) -> String?,     // LrcParser.toLrcText(...)
    private val settings: () -> DownloadSettings,              // autoDownloadOnPlay / limit
    private val onNotify: (String) -> Unit                     // → MainViewModel.showError
) {
    private val manualQueue = Channel<Pair<Song, Boolean>>(Channel.UNLIMITED)
    private val autoQueue   = Channel<Pair<Song, Boolean>>(Channel.UNLIMITED)

    init { scope.launch { loop() } }   // 单消费者：手动优先

    fun enqueue(song: Song, auto: Boolean) {
        scope.launch { (if (auto) autoQueue else manualQueue).send(song to auto) }
    }

    suspend fun downloadNow(song: Song, auto: Boolean): DownloadResult { /* 见 §5.3 */ }
}
```

**并发策略**：串行 1 个（手动队列优先），避免抢占播放带宽；队列容量 `Channel.UNLIMITED`，重复入队在 `downloadNow` 内幂等拦截。

### 5.3 单曲下载实现（要点）

```kotlin
suspend fun downloadNow(song: Song, auto: Boolean): DownloadResult = withContext(Dispatchers.IO) {
    val key = song.downloadKey
    val existing = repo.get(key)
    if (existing?.status == DownloadStatus.COMPLETED) return@withContext DownloadResult.Already
    if (existing?.status == DownloadStatus.DOWNLOADING) return@withContext DownloadResult.Duplicated

    // 去重：同一首歌（标题+艺术家规范化）已有完成记录 → 直接复用，不重复下载
    repo.findCompletedByDedupe(song.dedupeKey)?.let { return@withContext DownloadResult.Already }

    if (auto && repo.countAutoCompleted() >= settings().autoDownloadLimit) {
        notifyQuotaOnce(settings().autoDownloadLimit)      // 节流 5 分钟
        return@withContext DownloadResult.QuotaExceeded
    }

    val url = resolver.resolve(song) ?: return@withContext fail(key, "无法获取下载链接")
    val estimated = headContentLength(url) ?: estimateFromSong(song)
    if (!storage.hasRoomFor(estimated)) { storage.notifyFullOnce(); return@withContext fail(key, "存储空间不足") }

    val p = paths.build(song, extOf(url, song))
    p.artistDir.mkdirs(); p.albumDir.mkdirs(); p.tmpFile.parentFile?.mkdirs()
    repo.upsert(newEntity(key, song, status = DOWNLOADING, autoDownloaded = auto, tmpPath = p.tmpFile.absolutePath))

    downloadFile(url, p.tmpFile, estimated) { progress, written ->
        repo.updateProgress(key, progress)
        if (written % (512 * 1024) < 8192 && !storage.hasRoomFor(0)) throw StorageFullException()
    }

    coverWriter.writeArtistCover(p.artistDir, song)
    val coverBytes = coverWriter.writeAlbumCover(p.albumDir, song)
    val lrc = runCatching { lyricsProvider(song) }.getOrNull()

    val embedded = tagWriter.embed(p.tmpFile, song, coverBytes, lrc)
    if (!embedded) {                          // 旁路
        lrc?.let { File(p.albumDir, "${p.baseName}.lrc").writeText(it, Charsets.UTF_8) }
        coverBytes?.let { File(p.albumDir, "${p.baseName}.jpg").writeBytes(it) }
    }

    if (!p.tmpFile.renameTo(p.finalFile)) return@withContext fail(key, "文件保存失败")
    repo.upsert(entity.copy(status = COMPLETED, progress = 100, audioPath = p.finalFile.absolutePath,
        embedded = embedded, fileSize = p.finalFile.length(), completedAt = System.currentTimeMillis()))
    DownloadResult.Success(p.finalFile)
}
```

### 5.4 多源直链（`StreamUrlResolver`）

```kotlin
class StreamUrlResolver(
    private val adapter: () -> BackendAdapter?,                 // backendRegistry.getAdapter()
    private val network: suspend (Song) -> String?,             // NetworkMusicManager::resolvePlayUrl
    private val baidu: suspend (Song) -> String?                // BaiduStreamFactory（带 UA）
) {
    suspend fun resolve(song: Song): String? = when {
        song.isLocalSong -> null
        song.networkSource == BAIDU_SOURCE -> baidu(song)
        song.isNetworkSong -> network(song)
        else -> withContext(Dispatchers.IO) {
            runCatching { adapter()?.getStreamUrl(song.id) }.getOrNull()
        }
    }

    /** 电台等纯流媒体不可下载；本地歌曲无需下载 */
    fun isDownloadable(song: Song): Boolean =
        !song.isLocalSong && song.networkSource != RADIO_SOURCE
}
```

> `BAIDU_SOURCE` / `RADIO_SOURCE` 取 `data/model/SourceIdentifier.kt` 与 `RadioStation.SOURCE_ID` 的实际常量值。

### 5.5 崩溃恢复（`NasMusicApp.onCreate` 内，applicationScope）

1. 删除 `Music/.tmp/` 下所有 `.part`；
2. `UPDATE download_songs SET status='FAILED', errorMsg='已中断' WHERE status IN ('PENDING','DOWNLOADING')`；
3. 校验 `COMPLETED` 记录文件是否仍存在，缺失 → `FAILED('文件缺失')`（SD 卡拔出 / 用户手删）；
4. `StorageGuard.start()`：启动 30s 轮询 + 低存储广播监听。

### 6.3 实现

```kotlin
object MediaTagWriter {

    private val EMBEDDABLE = setOf("mp3", "flac", "m4a", "mp4", "aac", "ogg", "opus")

    /** 全局一次性配置：MP3 统一写 ID3v2.3 + 歌词语言 chi（在 NasMusicApp.onCreate 调用） */
    fun configure() {
        TagOptionSingleton.getInstance().id3v2Version = ID3V2Version.ID3_V23
        TagOptionSingleton.getInstance().isId3v23DefaultTextEncoding = true   // UTF-16，Win 兼容
    }

    fun supportsEmbedding(file: File) = file.extension.lowercase() in EMBEDDABLE

    /** @return true=已内嵌；false=不支持或失败 → 调用方写旁路文件 */
    fun embed(file: File, song: Song, coverJpeg: ByteArray?, lrcText: String?): Boolean {
        if (!supportsEmbedding(file)) return false
        return try {
            val audioFile = AudioFileIO.read(file)
            val tag = audioFile.tagOrCreateAndSetDefault
            tag.setField(FieldKey.TITLE, song.title)
            tag.setField(FieldKey.ARTIST, song.artist)
            tag.setField(FieldKey.ALBUM, song.album)
            if (song.trackNumber > 0) tag.setField(FieldKey.TRACK, song.trackNumber.toString())
            song.year?.let { tag.setField(FieldKey.YEAR, it.toString()) }
            song.genre?.takeIf { it.isNotBlank() }?.let { tag.setField(FieldKey.GENRE, it) }

            coverJpeg?.let { bytes ->
                tag.deleteField(FieldKey.COVER_ART)
                tag.setField(ArtworkFactory.createArtwork().apply {
                    binaryData = bytes
                    mimeType = "image/jpeg"
                    pictureType = 3                     // front cover
                })
            }

            lrcText?.takeIf { it.isNotBlank() }?.let { tag.setField(FieldKey.LYRICS, it) }

            audioFile.commit()
            true
        } catch (e: Exception) {
            AppLog.w("MediaTagWriter", "embed failed: ${e.message}", e)
            false
        }
    }
}
```

注意：
- 歌词**不写入** `AppSettings.lyricsOffsetMs`（那是播放期补偿），文件保持原始时间轴。
- `FieldKey.LYRICS` 在 jaudiotagger 中映射到 MP3 的 `USLT`、FLAC/OGG 的 `LYRICS`、MP4 的 `©lyr`。
- USLT 语言代码默认 `eng`；如需中文可 `TagOptionSingleton.getInstance().setLyrics3Language("chi")`（Spike 时确认 API 名）。
- 内嵌失败**不阻断**下载（降级旁路）。

### 7.1 数据库（**v2 修正：独立建库**）

> 选型依据见 §2.2（四问判定表）与 §2.3（下载功能落位表）：下载任务索引命中①（查询/聚合）与②（局部更新），必须用数据库；歌曲/封面/歌词正文一律不进库。

### 7.5 已下载歌曲并入本地曲库（**v2.2 修订：统一索引，不再单独成流**）

> **v2.1 之前的设计（废弃）**：维护独立的 `_downloadedSongs` 流，与 `_localSongs` 并行，在 `MainViewModel` 的 3 处 `allSongs` 拼接点各加一份。

**(1) `MusicScanner.scanPath()` 增加过滤与元数据短路**（`backend/local/MusicScanner.kt:116`）

```kotlin
suspend fun scanPath(
    rootPath: String,
    storageType: StorageType = StorageType.USB,
    excludeDirs: Set<String> = emptySet(),                  // 新增：排除 Music/.tmp
    metadataResolver: ((File) -> ScannedSong?)? = null      // 新增：命中则跳过 MMR
): List<ScannedSong> = withContext(Dispatchers.IO) {
    val root = File(rootPath)
    if (!root.exists() || !root.isDirectory) return@withContext emptyList()
    root.walkTopDown()
        .onEnter { dir ->                                   // 跳过 .tmp / 含 .nomedia 的目录
            dir.name !in excludeDirs && !File(dir, ".nomedia").exists()
        }
        .maxDepth(MAX_SCAN_DEPTH)
        .filter { it.isFile && it.extension.lowercase() in SUPPORTED_EXTENSIONS }
        .mapNotNull { file -> metadataResolver?.invoke(file) ?: scanFile(file, storageType) }
        .toList()
}
```

> **为什么要短路**：`scanFile()` 对每个文件都要 `MediaMetadataRetriever.setDataSource + 3×extractMetadata`，上千首的下载目录会让启动增量扫描卡到秒级。下载时元数据已写进 `downloads.db`，直接构造 `ScannedSong` 可跳过 MMR。

**(2) `LocalMusicRepository.incrementalScan()` 合并下载目录**（`backend/local/LocalMusicRepository.kt:36`）

### 7.6 与 USB / MediaStore 本地歌曲并存

#### 7.6.1 风险：MediaStore 可能重复收录下载目录

`getExternalFilesDir(DIRECTORY_MUSIC)` 落在 `/storage/emulated/0/Android/data/<pkg>/files/Music`。**不同 Android 版本行为不一致**（Android 11+ 分区存储下通常不索引，部分 ROM / 旧版本会索引），因此：

- ❌ **不能依赖 MediaStore 收录**（所以必须走 `scanPath` 文件通道）；
- ✅ **也不能假设它不收录**（所以必须 `distinctBy(path)` 去重）。

若不加去重，同一文件会有两条记录，主键不同（MediaStore `_ID` vs `stablePathHash64`）。`local_songs` 的 `path` 有 **唯一索引** + `@Insert(onConflict = REPLACE)`：SQLite `INSERT OR REPLACE` 遇唯一冲突会**删掉冲突行再插入**，所以不会崩，但结果是"静默二选一"且顺序依赖 —— 不可预测。显式 `distinctBy` 优先保留 `DOWNLOAD` 通道（元数据来自 `downloads.db`，比 MediaStore 更准）。

**是否给下载根目录放 `.nomedia`**：

| 方案 | 效果 | 取舍 |
|------|------|------|
| **不放**（默认） | 系统播放器/文件管理器可见 `Music/` 目录；靠 `distinctBy` 去重 | 少量 ROM 上会有瞬时的双条目（已去重，无实害） |
| 放 | 彻底阻断 MediaStore，扫描更快 | 用户在电视文件管理器里看不到下载目录，与需求 2 的"可管理目录"直觉冲突 |

默认不放；若实测（Spike 任务 0 附带验证项）发现重复严重，改为放 `.nomedia` 并保留文件通道扫描。

#### 7.6.2 USB 插拔互不影响

- `StorageMonitor.onDeviceMounted` → `scanUsbDevice()`（:111-122）只按 `storageType == "USB"` 过滤，**不会波及 `DOWNLOAD` 条目**。
- 反向也成立：USB 拔出时下载歌曲照常可播（在内置存储上）。
- 增量扫描的"卷挂载才比对"保护（B4 修复）对 `DOWNLOAD` 不适用也不需要 —— 下载目录始终存在。

#### 7.6.3 三源并存时的 UI 表现

现有：`allSongs = NAS 分页 + _localSongs + 百度`（`MainViewModel.kt:2310 / 2399 / 2447`），**跨源不去重**。因此同一首歌可能在列表中出现两条：

| 条目 | id | 来源徽章 |
|------|----|----------|
| 网络搜索结果 | `ntwk_netease_123` | 🌐 网络 |
| 已下载副本 | `local_<hash>` | ⬇ 已下载 |
| NAS 原始（若同时连着） | 后端原始 ID | 🎵 NAS |

处理策略（**需用户确认 D3**）：

- **P0（默认）**：不去重，但给已下载条目打专属徽章 —— `MusicSourceType` 新增 `DOWNLOAD("已下载", "⬇", Color(0xFF22D3EE))`，`Song.sourceType` 扩展属性加分支 `storageType == "DOWNLOAD" -> DOWNLOAD`（`data/model/SourceIdentifier.kt:44`）。
- **P1**：播放/加入队列时"已下载优先"（离线可播、省流量），按 `dedupeKey` 命中则替换成 `local_` 版本。
- **P2**：列表层按 `dedupeKey` 全局去重，只保留本地版 —— 会改变现有 UI 行为（NAS 与网络同名歌曲不再各显示一条），谨慎。

#### 7.6.4 扫描性能

`LocalSongEntity.lastModified` 字段已在表里但 **DAO 从未使用**。启用它做变更比对，避免每次启动对未变更文件重复 MMR：

| **总开关** | 缓存管理 → 离线下载 →「启用本地下载」 | 关 = 禁止一切下载（按钮隐藏、自动下载停）；已下载歌曲**仍可播放**，不删文件 |

| **删除单曲** | 歌曲行 ⬇ 按钮在 `Completed` 态时点击 ✓ | 二次确认 → 只删这一首（文件 + 索引），不影响同专辑其他曲目 |
| **下载中取消** | 歌曲行 ⇣ 按钮 | 取消任务 + 删 `.part`，回到 `Idle` |
| **导出到 USB** | 缓存管理 → 离线下载 →「导出到外接设备」 | 选设备 → 授权 → 复制文件（含封面/歌词）→ 扫描入库（§8.8） |

> 现有缓存清理项（歌词/封面/MV/伴奏）都是**点了直接清、无确认**。删除用户下载的音乐文件破坏性更大，因此清空/删除单曲**必须**二次确认；而"清除缓存类"保持现有风格不变。

#### 8.7.4 边界情况

| 场景 | 处理 |
|------|------|
| 正在播放的就是被删文件 | 先 `stop()` 再删；已在上面代码处理 |
| 正在下载的任务 | `cancelAll()` 取消 + 删 `.part`；不让其写回 `COMPLETED` |
| 文件被 ExoPlayer 持有 fd | Android 上删除已打开文件通常成功（fd 保持可读），删不掉时标记 `FAILED` 并提示重启后重试 |
| 清空后 | 立即刷新 `StorageGuard` 可用空间与设置页统计（0 首 / 0 MB） |
| 总开关关闭时机 | **已入队任务跑完**（用户已明确触发），不再新增；自动下载立即停止 |
| 总开关关闭时点下载按钮 | 按钮不渲染（`onDownload` 传 null），列表不留空位；避免"点了没反应" |
| 总开关关闭但仍触发了自动下载 | `AutoDownloadController` 判定链第一步即 `downloadEnabled`，直接返回 |
| USB 拔出 | 下载目录在内置存储，清空/删除不受影响 |
| 删除后同名歌曲重新下载 | `dedupeKey` 换新记录，路径冲突走 `(2)` 后缀（§4.3） |

### 8.8 导出到外接设备（USB / SD）

> 对应需求 10。入口：设置页 → 缓存管理 → 离线下载 →「导出到外接设备」。
> 前置依赖：§4 目录结构、§5 下载状态机、§7.5 已下载歌曲并入本地索引。

#### 8.8.1 范围与非目标

| 项 | 结论 |
|------|------|
| **导出什么** | `downloads.db` 中 `state = COMPLETED` 的全部歌曲：**音频文件 + `artist.jpg` + `cover.jpg` + 旁路的 `.lrc` / 同名 `.jpg`** |
| **不导出什么** | `downloads.db` 索引本身、App 设置、播放记录、歌手/专辑以外的缓存 |
| **是否重新编码** | **否**。源文件在下载时已内嵌封面与歌词（§6），导出就是**字节复制**，不调 `MediaTagWriter` |
| 非目标 | 反向导入（USB → 本地库，现有 `scanUsbDevice()` 已能读）、按歌单选择性导出（P2）、增量同步删除（即源删了目标跟着删，P2） |

#### 8.8.2 写入权限路径选型（**本节是整章的设计基础**）

Android 10（API 29）起，App 无法用 `File` API 直接写外接存储根目录。可选路径实测如下：

| 方案 | 机制 | 权限 | TV 可用性 | 目录结构自由度 | 结论 |
|------|------|------|-----------|----------------|------|
| **A. SAF 目录树授权** | `ACTION_OPEN_DOCUMENT_TREE` + `takePersistableUriPermission` → `DocumentFile` | 用户一次性授权 | ⚠️ **不可靠** | ✅ 完全自由 | **首选，但必须有兜底** |
| B. `StorageVolume.createAccessIntent()` | 系统授权页授予整个卷 | 用户授权 | ❌ **API 29 已废弃**，Android 10+ 启动后立即 `RESULT_CANCELED` | ✅ | **排除** |
| **C. 应用专属目录** | `Context.getExternalFilesDirs()` 取 USB/SD 上的 `/storage/XXXX-XXXX/Android/data/<pkg>/files/` | **无需任何权限** | ✅ **100% 可用** | ✅ 该目录内完全自由 | **必选兜底** |
| D. All Files Access | `MANAGE_EXTERNAL_STORAGE` + 引导到系统设置页授权 | 用户在 Settings 手动开 | ⚠️ 取决于 ROM 是否暴露该设置页 | ✅ | 高级选项（P2） |
| E. MediaStore 按卷写入 | `MediaStore.Audio.Media.getContentUri(volumeName)` + `RELATIVE_PATH` | 无需 | ✅ | ❌ **只能写媒体集合** | **不满足需求** |

**E 被排除的理由**（重要）：MediaStore 只能写入受管媒体集合。音频可写 `Music/<歌手>/<专辑>/`，但**`.lrc` 不是受管媒体类型，根本写不进去**；`artist.jpg` 走 Images 集合时 `RELATIVE_PATH` 又被限制在 `Pictures/` 之下。需求 2/3/4 要求的 `music/歌手/专辑/` 三层结构 + 同名旁路文件，**MediaStore 无法完整表达**。

**最终策略：A 优先 → C 兜底，D 预留**

```
点「导出到外接设备」
      │
      ├─ 枚举 StorageMonitor.storageDevices 中 type ∈ {USB, EXTERNAL} 且 isMounted
      │      └─ 空 → 提示「未检测到外接存储设备」，按钮本就隐藏
      │
      ├─ 该设备是否已有持久化的 SAF 授权 URI？（DataStore）
      │      ├─ 有 → 校验权限仍有效（见 8.8.4）→ 直接走 A
      │      └─ 无 → 探测 SAF 可用性（8.8.3）
      │              ├─ 可用 → 发起 ACTION_OPEN_DOCUMENT_TREE → 走 A
      │              └─ 不可用 → 静默降级到 C（提示目标路径，不弹错）
      │
      └─ 走统一 ExportSink 抽象执行复制（A/C 对上层透明）
```

#### 8.8.3 SAF 可用性探测（**必须做，否则 TV 上会崩**）

Android TV 上 SAF 的有无**无法靠文档推断**，且常规探测手段会失灵：

- 部分 TV（NVIDIA Shield）有完整 SAF；部分（Xiaomi Mi Box 及相当一批 TV）**没有 DocumentsUI**。
- 对 `ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT`，`resolveActivity()` **不为 null**，但返回的是 Google 的桩实现
  `com.google.android.tv.frameworkpackagestubs/.Stubs$DocumentsStub`——启动后只会弹一句 "You don't have an app that can do this"。
- 对 `ACTION_OPEN_DOCUMENT_TREE`，桩实现通常**不存在**，`resolveActivity()` 返回 null，可以正常探测。

```kotlin
// backend/export/ExportPermissionHelper.kt
object ExportPermissionHelper {

    /** TV 上的 SAF 桩实现，命中即视为不可用 */
    private const val TV_STUB_PKG = "com.google.android.tv.frameworkpackagestubs"

    /**
     * 判断 ACTION_OPEN_DOCUMENT_TREE 是否真的可用。
     * 注意：只探测 TREE，不要拿 OPEN_DOCUMENT 的探测结果类推。
     */
    fun isTreePickAvailable(context: Context): Boolean {
        val intent = Intent(Intent.ACTION_OPEN_DOCUMENT_TREE).apply {
            addFlags(Intent.FLAG_GRANT_PERSISTABLE_URI_PERMISSION)
            addFlags(Intent.FLAG_GRANT_WRITE_URI_PERMISSION)
            addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
        }
        val ri = intent.resolveActivity(context.packageManager) ?: return false
        // 双保险：resolveActivity 非 null 也可能是桩
        val pkg = ri.activityInfo?.packageName
        return pkg != null && pkg != TV_STUB_PKG
    }
}
```

> **仍必须 `try/catch ActivityNotFoundException`**：部分 ROM 的 `resolveActivity()` 与实际可启动性不一致。捕获后降级到方案 C，不要让用户看到崩溃或误提示。

#### 8.8.4 授权发起与持久化

**项目当前没有任何 `registerForActivityResult` / `onActivityResult`**（全量 grep 确认），需在唯一的 `MainActivity` 中新增注册：

```kotlin
// MainActivity.kt（补充）
private val exportTreeLauncher = registerForActivityResult(
    ActivityResultContracts.StartActivityForResult()

    if (result.resultCode != Activity.RESULT_OK) return@registerForActivityResult

    (application as NasMusicApp).exportCoordinator.onTreeGranted(uri)
}

        addFlags(Intent.FLAG_GRANT_WRITE_URI_PERMISSION)
    }

        .onFailure { (application as NasMusicApp).exportCoordinator.onTreeUnavailable() }
```

**持久化与校验**：

| 环节 | 做法 |
|------|------|
| 存储 | `AppPreferences` 新增 `export_tree_uri: String?` + `export_volume_id: String?`（DataStore 标量，命中 §2.2 规则 ③） |

| 授权被用户撤销 | 同上，重新走流程，不报错 |

#### 8.8.5 目标根目录与目录结构

**完全复用 §4 的 `DownloadPathBuilder`**，不另写一套（避免两套清洗规则产生分歧）：

| 方案 | 根前缀 | 完整示例 |
|------|--------|----------|
| A（SAF） | 用户选择的目录 + `NASMusic/` | `<用户选的 U 盘根目录>/NASMusic/周杰伦/七里香/01 - 七里香.mp3` |
| C（应用专属） | `getExternalFilesDirs(DIRECTORY_MUSIC)` 中匹配该卷的那个 | `/storage/1234-ABCD/Android/data/com.nasmusic.tv/files/Music/周杰伦/七里香/01 - 七里香.mp3` |

方案 A 统一加 `NASMusic/` 子目录——用户可能选到 U 盘根目录，直接往里铺几十个歌手目录不礼貌。

```kotlin
/** 把 StorageDevice 解析成实际可写的根（A 优先，C 兜底） */
fun resolveRoot(device: StorageDevice): ExportRoot {
    // A：已授权的 SAF 树
    val uri = prefs.exportTreeUri.first()
    if (uri != null && device.id == prefs.exportVolumeId.first() && hasPersistedWrite(uri)) {
        return ExportRoot.Saf(DocumentFile.fromTreeUri(context, uri)!!.let { tree ->
            tree.findFile(EXPORT_DIR) ?: tree.createDirectory(EXPORT_DIR)!!   // "NASMusic"
        })
    }
    // C：应用专属目录（无权限要求）
    val dirs = context.getExternalFilesDirs(Environment.DIRECTORY_MUSIC)
    val match = dirs.firstOrNull { it != null && it.absolutePath.startsWith(device.path) }
    return if (match != null) ExportRoot.File(match) else ExportRoot.Unavailable
}
```

> `getExternalFilesDirs()` 对已挂载的 USB/SD 会返回对应卷上的路径；数组第一个元素恒为主存储。用 `startsWith(device.path)` 匹配即可定位。

#### 8.8.7 导出流程与状态机

```kotlin
sealed interface ExportState {
    object Idle : ExportState
    data class Preparing(val total: Int) : ExportState              // 校验空间/授权/枚举文件
    data class Running(val done: Int, val total: Int, val current: String,
                       val skipped: Int = 0, val failed: Int = 0) : ExportState
    data class Completed(val done: Int, val skipped: Int, val failed: Int,
                         val freed: Long = 0L) : ExportState
    data class Failed(val reason: ExportError) : ExportState
    object Cancelled : ExportState
}

enum class ExportError { NO_DEVICE, NO_PERMISSION, NO_SPACE, DEVICE_REMOVED, IO, NOTHING_TO_EXPORT }
```

**执行流程**（`SongExporter`，运行在 `Dispatchers.IO`）：

```
1. 枚举待导出：downloads.db 中 state=COMPLETED 的条目
   ├─ 逐条校验源文件存在且 size 匹配（文件可能被外部删除，复用 §5.5 崩溃恢复的校验逻辑）
   └─ 展开为「文件任务」：音频 1 个 + cover.jpg + artist.jpg（去重，同专辑只导一次）+ 旁路 .lrc/.jpg
2. 空 → Failed(NOTHING_TO_EXPORT)
3. 空间校验：sum(待导文件字节) > device.availableSpace - 100MB → Failed(NO_SPACE)
   （导出目标也留 100MB 余量，与 §10 内部存储守护同口径；中途每 50MB 复检一次）
4. 增量过滤：查 export_records(volumeId)，relPath 已存在 且 srcSize 未变 → skipped++
5. 逐个复制：8KB 缓冲流；每完成一个文件 upsert 一条 record；每完成 1 首歌 done++
6. 每首歌结束后检查 isActive，取消 → 保存已完成记录，退出（可续跑）
7. 完成 → 触发媒体扫描（8.8.8）→ Completed(done, skipped, failed)
```

**关键实现约束**：

| 约束 | 原因 / 做法 |
|------|-------------|
| 复制用 `input.use { }` / `output.use { }` | SA F 的 `OutputStream` 不 close 会导致目标文件 0 字节 |
| 先写 `.part` 再 rename（方案 C）；SAF 下直接写目标 | SAF 无 rename 语义，改为「写失败即 `delete()`」，靠 `export_records` 保证不残留半截被当作已完成 |
| `artist.jpg` / `cover.jpg` 按目录去重 | 一张专辑 12 首歌不能写 12 次同一个 `cover.jpg` |
| 目录创建逐层 `createDirectory` 并判空 | SAF 下 `createDirectory` 可能返回 null（同名文件已存在）→ 回退 `findFile` |
| 取消要响应及时 | 复制循环内检查 `isActive`，8KB 粒度足够（秒级响应） |
| 进度更新节流 | 每完成 1 首歌 emit 一次，不要每 8KB emit（Compose 重组风暴） |

#### 8.8.8 导出后处理

| 事项 | 做法 |
|------|------|

### 9.2 判定链

```kotlin
class AutoDownloadController(
    private val settings: () -> DownloadSettings,
    private val repo: DownloadRepository,
    private val storage: StorageGuard,
    private val resolver: StreamUrlResolver,
    private val manager: SongDownloadManager,
    private val notify: (String) -> Unit
) {
    private var lastQuotaNotifyAt = 0L

    suspend fun onSongChanged(song: Song) {
        if (!settings().autoDownloadOnPlay) return
        if (!resolver.isDownloadable(song)) return
        if (repo.get(song.downloadKey) != null) return                    // 已下载/失败过，不自动重试
        if (repo.findCompletedByDedupe(song.dedupeKey) != null) return

        val limit = settings().autoDownloadLimit
        if (repo.countAutoCompleted() >= limit) {
            val now = System.currentTimeMillis()
            if (now - lastQuotaNotifyAt > 5 * 60 * 1000) {
                lastQuotaNotifyAt = now
                notify(Res.string(R.string.msg_download_quota_reached, limit))
            }
            return
        }
        if (!storage.hasRoomFor(estimateFromSong(song))) { storage.notifyFullOnce(); return }

        manager.enqueue(song, auto = true)
    }
}
```

| 项 | 设计 |
|----|------|
| 触发时机 | 歌曲一切换即触发（不等播放进度），避免"切太快没下到" |
| 失败的自动任务 | **不自动重试**（避免失败循环），仅保留 ✕ 供用户手动重试 |
| 手动优先 | 手动队列非空时，自动任务不抢占 |
| 网络类型 | 本期不限制（TV 多为有线/WiFi）；P2 可加"仅 WiFi" |

## 10. 存储守护（需求 9）

### 10.1 判定（**v2 修正：双 StatFs 取 min**）

应用专属外部目录 `/sdcard/Android/data/...` 在多数设备上由 `/data` 分区（sdcardfs/fuse）承载，只看 `StatFs(downloadRoot)` 会**高估**可用空间。必须取两者的较小值：

```kotlin
class StorageGuard(private val context: Context, private val rootProvider: () -> File) {

    companion object {
        const val RESERVED_BYTES = 100L * 1024 * 1024      // 需求 9：至少保留 100MB
        const val SAFE_BUFFER_BYTES = 5L * 1024 * 1024     // 写入抖动缓冲
    }

    private val _availableBytes = MutableStateFlow(0L)
    val availableBytes: StateFlow<Long> = _availableBytes.asStateFlow()

    /** 取「下载根目录所在分区」与「内部数据分区」的较小可用值 */
    fun availableBytes(): Long = listOfNotNull(rootProvider(), context.filesDir)
        .minOf { runCatching { StatFs(it.absolutePath).availableBytes }.getOrDefault(0L) }

    fun hasRoomFor(estimatedBytes: Long): Boolean =
        availableBytes() - RESERVED_BYTES - SAFE_BUFFER_BYTES > estimatedBytes

    fun isStorageFull(): Boolean = availableBytes() <= RESERVED_BYTES

    fun start(scope: CoroutineScope) {
        scope.launch { while (true) { _availableBytes.value = availableBytes(); delay(30_000) } }
        context.registerReceiver(
            object : BroadcastReceiver() {
                override fun onReceive(c: Context?, i: Intent?) {
                    _pausedByLowStorage.value = isStorageFull()   // 触发队列暂停
                }
            },
            IntentFilter(Intent.ACTION_DEVICE_STORAGE_LOW)
        )
    }
}
```

`util/StorageUtils.kt` 抽取 `availableBytes(file)` / `formatSize(bytes)`，`StorageMonitor.kt:135` 的私有 `getAvailableSpace()` 改为调用它。

### 10.2 检查时机

| 时机 | 行为 |
|------|------|
| 入队前（手动/自动） | `hasRoomFor(estimated)` 失败 → 不入队 + 提示 |
| 下载中每 512KB | 复检；跌破 → 抛 `StorageFullException` → 删 `.part`、状态 FAILED、**暂停整个队列**直到空间恢复 |
| 30s 轮询 | 刷新 `_availableBytes`（设置页实时显示） |
| `ACTION_DEVICE_STORAGE_LOW` | 立即暂停队列 + 提示 |
| 进入设置页 | 立即刷新一次 |

### 10.3 大小预估

```
① HTTP HEAD → Content-Length
② 无 Content-Length → durationMs/1000 × bitrate/8
③ 再回退 → 8MB
```

## 16. 审阅发现的问题与修正（v1 → v2）

| # | 严重度 | v1 的问题 | 影响 | v2 修正 |
|---|--------|-----------|------|---------|
| 1 | **严重** | 数据库迁移写"v1→v2"，且计划把 `download_songs` 并入 `LocalMusicDatabase` | 该库实际已是 **v2** 且开启 **`fallbackToDestructiveMigration(true)`**：任何 schema 变更都会重建库 → 下载记录全丢、文件变孤儿、用户重复下载 | 独立 `DownloadDatabase`（downloads.db, v1）+ `reindexFromDisk()` 兜底（§7.1） |
| 2 | **严重** | jaudiotagger 坐标写成 `org:jaudiotagger:3.0.1` | 坐标不存在 → 依赖解析直接失败 | 改为 `net.jthink:jaudiotagger:3.0.1`，补 Android fork 与 LGPL 合规（§6.1） |
| 3 | **中** | 直接调用 `RowActionButton(text, color, onClick, enabled)` | 现有组件只有 3 个参数 → 编译失败 | 增加 `enabled: Boolean = true`（§11.1 改动 2） |
| 4 | **中** | `SettingActionButton(label, onClick)` 两参 | 实际是三参（label/description/onClick）→ 编译失败 | 按三参补齐（§8.4） |
| 5 | **中** | 封面计划调用 `AlbumCoverResolver.resolveCovers()` / `ArtistCoverResolver.resolveCovers()` | 二者是**批量** API（需 `List<Album>/<Artist>` + `allSongs` + 回调），单曲下载流程无法使用 | 改用 `song.coverUrl` → `NetworkMusicManager.searchCoverUrl()` → `ItunesCoverSearcher.searchTrack()`；歌手封面新增 `resolveArtistCoverUrl(name)`（§6.5） |
| 6 | **中** | 仅用 `song.id` 做幂等键 | 网络源 id = `ntwk_${source}_${sourceId}`，同一首歌在不同平台 sourceId 不同 → 重复下载 | 新增 `dedupeKey`（title+artist 规范化）+ 下载前查询（§7.3） |

## 18. 验收标准

1. 搜索任意可下载源歌曲 → 点 ⬇ → 文件落在 `Music/<歌手>/<专辑>/`，重启后仍在且可离线播放。
2. 歌手目录存在 `artist.jpg`，专辑目录存在 `cover.jpg`。
3. MP3/FLAC/M4A 用第三方播放器可看到内嵌封面与歌词；WAV 等生成同名 `.jpg` / `.lrc`。
4. 开关关闭 → 播放不产生下载；开启 → 自动下载当前播放歌曲。
5. 自动下载达到上限 → 停止并提示"已达设置的最大下载数量（N）"，5 分钟内不重复提示。
6. 可用空间不足（预留 100MB）→ 拒绝下载并提示；下载中途不足 → 中断并清理临时文件。
7. `./gradlew.bat assembleRelease` 通过；TV 与手机真机无回归。
8. 插入 U 盘→ 设置页出现「导出到外接设备」；拔出后该项自动消失。
9. 导出完成后 U 盘目录为 `NASMusic/<歌手>/<专辑>/`，含音频、`artist.jpg`、`cover.jpg` 与旁路 `.lrc`；电脑上用第三方播放器可直接播放。
10. 无 SAF 的 TV 机型上点击导出不崩溃，自动降级并完成导出。
11. 导出中拔盘 → 中止且提示；重新插入后再次导出仅处理未完成部分（增量）。
12. 重启 App 后 SAF 授权仍有效，无需重新授权即可导出。

## 一、背景与目标

### 1.1 需求（来自用户描述）

1. 支持从**百度网盘**播放用户保存的音乐文件
2. 支持**搜索**网盘中的音乐（关键词搜索 + 目录浏览）
3. 读取**音乐文件、歌词文件（或内嵌歌词）、封面图**等元数据
4. 将网盘歌曲**加入歌单**，确定**唯一值**，关联现有歌单 JSON
5. **搜索保存的 MV**，与歌曲文件或歌曲唯一值**关联**

### 1.2 设计原则

- **对齐现有架构**：百度网盘作为新的 `NetworkMusicService` 实现接入，复用 `Song` 模型（`ntwk_${source}_${sourceId}` ID 约定）、`LocalPlaylist` JSON 持久化、`PlayerManager.onNeedResolveStreamUrl` 延迟解析链路，零侵入主播放器
- **延迟解析**：百度 dlink 有 8h 有效期，与网络歌曲"streamUrl 播放时解析不持久化"的模型天然契合
- **参考但不照搬**：PureMusic / 流云音乐的鉴权与串流模式作为验证参考，但实现须对齐 NASMusicTV 的手动 DI 容器与 OkHttp 原生调用风格（不引入 Retrofit）
- **TV 优先**：鉴权用**设备码模式**（电视显示短码，手机输入，零打字），D-Pad 可导航

### 1.3 不做的事（范围约束）

- 不做网盘文件**上传/管理**（只读播放）
- 不做百度网盘**分享**功能
- 不替换现有 Jellyfin/Navidrome/Meting 后端，百度网盘是**并列的第四种音源**
- 不引入 Retrofit（现有适配器均用原生 OkHttp + Gson，保持一致）

## 二、现有架构对齐分析

> 以下结论来自 codegraph 对源码的逐符号调研，是本方案的设计基础。

### 2.1 BackendAdapter vs NetworkMusicService —— 选哪条路？

NASMusicTV 有两条音源接入路径：

| 路径 | 接口 | streamUrl 时机 | 典型实现 | 结构假设 |
|------|------|--------------|---------|---------|
| **NAS 后端** | `BackendAdapter` | `getStreamUrl(songId)` **同步**返回稳定 URL，列表加载时即填入 `Song.streamUrl` 持久化 | Jellyfin / Navidrome | 服务器有专辑/艺术家/流派结构 |
| **网络音乐** | `NetworkMusicService` | `resolvePlayUrl(song)` **异步**，播放时解析，`Song.streamUrl` 持久化为空 | Meting | 扁平搜索，无专辑结构 |

**百度网盘的特征**：
- dlink 下载链接**有 8 小时有效期**（与 Jellyfin 的永久 token URL 不同）——若走 `BackendAdapter.getStreamUrl()` 同步路径，列表加载时拿到的 URL 8h 后失效，用户午后打开的歌单晚上播不了
- 网盘是**扁平文件系统**，无专辑/艺术家/流派的服务端结构（虽有目录，但不是音乐库语义）
- 鉴权用 OAuth，不是 `initialize(baseUrl, apiToken, user, pass)` 的用户名/密码模型

**结论：百度网盘走 `NetworkMusicService` 路径**（与 Meting 同层），不走 `BackendAdapter`。具体：
- `Song.id = "ntwk_baidu_${fs_id}"`，`isNetworkSong = true`，`networkSource = "baidu"`，`networkId = fs_id`
- `Song.streamUrl = null`（持久化为空，播放时由 `BaiduNetdiskService.resolvePlayUrl()` 实时解析）
- 复用 `PlayerManager.onNeedResolveStreamUrl` 回调链路（`PlayerManager.kt:452`），网络歌曲进队列后 streamUrl 为空触发延迟解析
- 复用 `NetworkMusicManager.resolvePlayUrl()` 的 5min 缓存（`NetworkMusicManager.kt:88`，`PLAY_URL_CACHE_TTL_MS`），**TTL 保持 5 分钟不为百度源放宽**（§11 问题 6 结论：`CachedPlayUrl` 无按源区分 TTL 的结构，放宽需改数据结构；5min ≪ dlink 小时级有效期，方向安全）

### 2.2 Song 模型（`data/model/Song.kt:12`）

```kotlin
data class Song(
    val id: String,              // 百度: "ntwk_baidu_${fs_id}"
    val title: String,           // server_filename 去扩展名
    val artist: String = "",     // 百度 API 不返回元数据，留空（由歌词匹配反填）
    val artistId: String? = null,
    val album: String = "",
    val albumId: String? = null,
    val coverUrl: String? = null, // 侧车 cover.jpg / 网络匹配
    val streamUrl: String? = null,// null（播放时解析）
    val durationMs: Long = 0L,    // 百度 API filemetas 返回 duration 字段
    val trackNumber: Int = 0,
    val discNumber: Int = 1,
    val year: Int? = null,
    val genre: String? = null,
    val bitrate: Int = 0,         // filemetas 返回
    val isNetworkSong: Boolean = true,
    val networkSource: String? = "baidu",
    val networkId: String? = fs_id.toString()
)
```

> `fs_id` 是百度网盘文件的全局唯一标识，**跨重命名/移动保持稳定**（百度官方保证），适合做唯一值。

### 2.3 本地歌单 JSON（`data/model/LocalPlaylist.kt:10`；持久化逻辑在 `AppPreferences.kt:566`，v2 勘误：v1 误标 AppPreferences.kt:576）

`LocalPlaylist` 存于 DataStore，`songs` 字段是完整 `Song` 对象的 Gson 序列化 JSON：

```kotlin
data class LocalPlaylist(
    val id: String,              // 本地 UUID
    val name: String,
    val songs: List<Song> = emptyList(),  // 完整 Song 对象
    val createdAt: Long = System.currentTimeMillis()
)
```

**百度歌曲加入歌单零改动**：直接把 `Song(isNetworkSong=true, networkSource="baidu", networkId=fs_id, streamUrl=null)` 序列化进 `songs`。播放时 `LocalPlaylist` -> `playQueue` -> `PlayerManager` 发现 `streamUrl==null` -> `onNeedResolveStreamUrl(index)` -> `MainViewModel` -> `NetworkMusicManager.resolvePlayUrl(song)` 按 `networkSource="baidu"` 路由到 `BaiduNetdiskService`。

### 2.4 MV 系统（`backend/network/mv/`）

现有 MV 系统（`MvSearchManager` / `MvPersistentCache` / `BilibiliMvService`）的特征：
- `MvPersistentCache` 存 `Map<songId, MvCacheEntry>` 到 `filesDir/mv_cache.json`，只存 **bvid**（稳定）不存直链（过期）
- `MvSearchManager.searchMvFor(song)` 按 `song.id`（即 `ntwk_baidu_${fs_id}`）查缓存 -> 命中则 `resolveMv(bvid)` 拿新鲜直链
- `MvSearchService` 接口：`searchMv(title, artist, excludeBvids, minSimilarity)` + `resolveMv(bvid)`

**百度网盘本地 MV 的接入方式**：新增 `BaiduMvFileService implements MvSearchService`，在 `MvSearchManager.services` 列表中**排在 Bilibili 之前**（本地优先于在线）。当当前歌曲是百度歌曲（`networkSource=="baidu"`）时，先查同目录/同名 MV 文件；未命中再 fallback 到 Bilibili 在线搜索。关联键统一为 `song.id`，`MvPersistentCache` 无需改结构（`bvid` 字段语义泛化为"MV 唯一标识"，百度场景下存 `ntwk_baidu_mv_${mv_fs_id}`）。

### 2.5 歌词链路（`lyrics/LyricsManager.kt:74`）

`LyricsManager.getLyrics()` 调用 `BackendAdapter.getLyrics(songId)`（NAS 后端）和 `NetworkMusicManager.resolveLyrics(song)`（按 `networkSource` 路由）。百度源需在 `BaiduNetdiskService` 实现 `resolveLyrics(song)`，返回 LRC 文本。优先级：侧车 .lrc -> 内嵌 ID3 USLT -> 网络匹配 fallback。

### 2.6 人声消除（已实现）

`VocalRemovalProcessor.kt`（方案 B，实时 DSP Mid/Side）**已上线**（见 README 功能列表 + `docs/vocal-removal-approach-b-dsp.md`）。百度网盘歌曲播放时走的是同一个 ExoPlayer + 同一个 AudioProcessor 管线，**人声消除对百度歌曲自动生效，零额外开发**。流云音乐的同类功能仅作效果对照参考（见附录 §10）。

## 三、百度网盘开放平台 API 调研

> 以下结论来自百度网盘开放平台官方文档（https://pan.baidu.com/union/doc/）与多个开源 SDK（lfhy/xpan、baidu-netdisk/baidu-drive-sdk-go、creayhx/baidu-netdisk-sdk）的交叉验证。

### 3.0 API 版本基线追踪（必读）

> ⚠️ **百度网盘开放平台 API 无显式版本号**（不像 `/v2/xxx` 那样带版本路径，**也没有"查询当前 API 版本"的接口**），接口会**静默演进**：端点方法、参数、响应字段随时可能变更；旧字段可能保留也可能移除；`User-Agent` 约束、dlink 有效期、category 代码等行为也可能调整。**本方案所有 API 细节均以"调研日期"为基线，实施前必须重新验证。**
>
> **能获得的版本线索只有两个**：(a) URL 路径中的 `rest/2.0/`（平台级版本标识，多年保持稳定，可写入日志但价值有限）；(b) 各接口响应 JSON 的**字段结构**（字段增减即实际版本演进载体）——所以本节的"版本指纹"机制以**(b) 字段结构探测 + 本地基线对比 + 用户提示**为核心，见下方【版本管理机制】。

**基线记录（2026-08-20 websearch 调研）**：

| 项目 | 基线值 | 验证状态 |
|------|--------|---------|
| Authorization Code 授权端点 | `https://openapi.baidu.com/oauth/2.0/authorize` | ✅ 官方文档确认 |
| Token 端点 | `https://openapi.baidu.com/oauth/2.0/token` | ✅ 官方文档确认 |
| 设备码端点 | `https://openapi.baidu.com/oauth/2.0/device/code`（`response_type=device_code`，**此步无需 client_secret**） | ✅ 官方文档 + Rust SDK 交叉确认（v2 修正：v1 误写为 token 端点） |
| 范围 scope | 固定 `basic,netdisk` | ✅ 官方文档确认 |
| 文件接口 base | `https://pan.baidu.com/rest/2.0/xpan/multimedia` | ✅ 官方文档 + SDK 交叉验证 |

| 单页 limit | ≤ 1000 | ⚠️ SDK 交叉得出，实施前实测 |

| dlink 请求头 | `User-Agent: pan.baidu.com`（>20MB 文件必需） | ⚠️ 社区共识，实施前实测 403 行为 |
| refresh_token 有效期 | 10 年（网页授权 OAuth 文档） | ✅ 官方文档确认 |

> 上表"⚠️ 实施前实测"项是本方案落地时的**第一优先级验证清单**——任何一项与实测不符，都以实测为准并回填本表。

**版本管理机制**（代码层面）：

1. **集中常量表**：所有百度端点、method、参数、category 码集中在 `BaiduNetdiskConfig.kt` 的 companion 常量（不给散布在多个类中）。API 变更时**只改这一处**。
2. **本地基线固化**：本版 APK 在上线前实测验证通过的 API 字段结构，计算**字段指纹**（对探测端点响应的关键字段名+顺序做 SHA-256，或直接存字段名集合的规范序列化）写入常量 `BaiduNetdiskConfig.apiProbeBaseline`（随 App 版本固化），并同步回填到 `CloudDriveConfig.apiProbeBaseline`（§7）。
3. **启动版本探测**：登录成功后调用一次 `filemetas`（或 `uinfo` 等稳定端点）做**探针**：
   - 校验返回 JSON 中关键字段（`errno`、`list[0].fs_id`、`dlink` 等）存在性与类型
   - 用同一算法计算实测指纹，写入 `CloudDriveConfig.apiProbeResult`
4. **对比与用户提示**（关键闭环）：启动探测后对比 `apiProbeBaseline` vs `apiProbeResult`：
   - **一致**：静默通过，无任何打扰；`CloudDriveConfig.apiDrifted = false`
   - **不一致**（`apiDrifted = true`）：说明**百度已升级 API，本版实现可能已不兼容**，做两件事：
     - 记录 `AppLog.w("BaiduApi", "API drifted: baseline=$baseline probe=$probe")`
     - **提示用户**：`MainViewModel` 启动时检查 `apiDrifted`，置一个一次性高优先级提示（Toast/Snackbar："百度网盘 API 可能已升级，部分功能可能异常，请更新应用"），且设置页"百度网盘 → 高级 → API 健康状态"持续显示"⚠️ API 与当前版本不匹配"，点击展开差异摘要（缺了哪些字段）
   - 记忆化：提示只弹一次（写入 `AppPreferences` 的 `baiduApiDriftNotified` 标记），避免每次启动弹
5. **响应解析容错**：Gson 解析用 `JsonObject` 或 `@SerializedName` + `defaultValue`，**缺失字段不崩**（沿用 NavidromeAdapter 的 `MapNotNull`/`getOrElse` 模式）；关键字段缺失时 `AppLog.w("BaiduApi", "field X missing: <响应前 200 字符>")`，方便线上定位 API 变更点
6. **错误码映射表集中管理**：`errno` 错误码（-6 认证失败/-9 文件不存在/-111 限流等）统一映射到用户提示 + AppLog，新错误码出现时能识别（而不是 UI 莫名失败）
7. **变更响应清单**：若用户报告功能异常且 `apiDrifted=true` → 走 §9 "百度 API 升级" 风险应对：核对官方文档 → 更新 `BaiduNetdiskConfig.kt` 常量表 + 新基线指纹 → 回填本表基线 → 发版。新版上线后 `apiProbeBaseline` 更新，`apiDrifted` 自动恢复 `false`。

### 3.1 OAuth 2.0 鉴权

百度开放平台支持三种授权模式：

| 模式 | 适用场景 | Access Token 有效期 | 可否刷新 | 是否需要 client_secret |
|------|---------|:---:|:---:|:---:|
| **授权码模式**（Authorization Code） | 有 Server 端 | 30 天 | ✅ refresh_token 有效期 **10 年** | ✅ 需要 |
| **简化模式**（Implicit Grant） | 无 Server 端 | 30 天 | ❌ 不可刷新，过期需重新登录 | ❌ 不需要 |
| **设备码模式**（Device Code） | 弱输入设备（无浏览器/电视/手表） | 30 天 | ✅ | ✅ |

**TV 场景选型**：**设备码模式（Device Code）**——专为电视等弱输入设备设计，无需 `redirect_uri`，无需手动输入长 code。
- 电视显示短设备码（如 `ABCD-1234`，4-8 位），用户用手机访问 `https://openapi.baidu.com/device` 输入即可
- Access Token 30 天，过期后支持刷新
- 需 `client_secret`，与授权码模式相同
- 已有开源 Go/Rust SDK 实现验证（`baowuhe/go-bdisk`、`creayhx/baidu-netdisk-sdk` 均支持 device code 流程）

**备选**：若用户偏好扫码，也可用授权码模式 + `display=tv&qrcode=1`，但需处理 `redirect_uri=oob` 手动输入 code 的问题（见 §11 待评审问题 2 结论）。

**设备码模式鉴权流程**：
```
1. 电视请求设备码：
   GET https://openapi.baidu.com/oauth/2.0/device/code?
       response_type=device_code
       &client_id={APP_KEY}
       &scope=basic,netdisk

   ⚠️ 端点是 /oauth/2.0/device/code（不是 token 端点），参数名是 response_type
   （不是 grant_type），且此步不需要 client_secret——第 3 步轮询换 token 时
   才需要 client_id + client_secret。

   返回：
   {
     "device_code": "xxxxxxxxxxxxxxxxxxxxxxxx",
     "user_code": "ABCD-1234",          ← 短码，4-8 位字母数字
     "verification_url": "https://openapi.baidu.com/device",
     "qrcode_url": "https://openapi.baidu.com/device/qr?code=ABCD-1234",
     "expires_in": 300,                  ← 5 分钟有效
     "interval": 5                       ← 轮询间隔（秒）
   }

2. 电视显示 user_code + verification_url（或 qrcode_url 生成二维码），
   提示用户"在手机上访问 https://openapi.baidu.com/device，输入验证码 ABCD-1234"

3. 电视轮询 token（每 interval 秒一次，直到 expires_in 超时或用户取消）：
   GET https://openapi.baidu.com/oauth/2.0/token?
       grant_type=device_token
       &code={device_code}
       &client_id={APP_KEY}
       &client_secret={SECRET_KEY}

   返回：
   { "access_token": "...", "refresh_token": "...", "expires_in": 2592000 }

   常见轮询错误码：
   - 40024 "authorization_pending" → 用户尚未完成授权，继续轮询
   - 40025 "authorization_declined" → 用户拒绝授权，终止轮询
   - slow_down → 轮询过频，增加间隔（当前 interval × 2）

4. 后续 token 刷新同授权码模式（grant_type=refresh_token）。
   ⚠️ refresh_token 单次有效：刷新响应会返回新的 refresh_token，必须与
   access_token 一并原子保存；刷新失败时旧 refresh_token 即失效，需重新走
   设备码授权（详见 §6.1.2）。
```

**Token 存储**：`access_token` + `refresh_token` + `expires_at` 存入 DataStore（加密敏感字段，参照现有 `AppPreferences` 的 `CryptoUtils` 用法）。`AppPreferences` 按 `CloudDriveType` 存取 token（`CloudDriveConfig.tokens`，见 §7；v1 的扁平 `baiduTokens` key 方案已被取代）。

**备用方案**：若开源嵌入 `client_secret` 有顾虑，可支持用户在设置页填入自己的 AppKey/SecretKey（百度开放平台个人注册门槛低，免费额度足够个人使用）。

### 3.2 文件列表与搜索

> 📌 本小节参数已对照 **BoxPlayer 开源实现**（`src/cloudbaidu/dirfilelist.ts`、`filecmd.ts`，2026-08 实测运行中）逐项核实。**文件列表与搜索走 `/xpan/file` 端点，文件元数据/dlink 走 `/xpan/multimedia` 端点**——两者 base 不同，勿混用（早期文档把三者都挂在 `/xpan/multimedia` 下，已修正）。

**统一入口**：

| 用途 | Base URL |
|------|----------|
| 列表 / 搜索 | `https://pan.baidu.com/rest/2.0/xpan/file` |
| 元数据 / dlink | `https://pan.baidu.com/rest/2.0/xpan/multimedia` |

| method | 端点 | 关键参数（BoxPlayer 实证） |
|--------|------|---------|
| `list` | `/xpan/file` | `dir`, `order`(`name`/`time`/`size`), `desc`(0/1), `start`, `limit`(≤1000), `web=1`(返回缩略图 thumbs), `folder=0` |
| `search` | `/xpan/file` | **`key`**（不是 `word`！）, `dir`, `num`(单页≤500), `recursion=1`, `web=1` |
| `filemetas` | `/xpan/multimedia` | `fsids=JSON数组`, `dlink=1`, `thumb=1`, `extra=1`, `needmedia=1`, `detail=1` |

> ⚠️ **search 参数是 `key` 不是 `word`**（BoxPlayer `dirfilelist.ts:99` 实证：`method=search&key={keyword}&num=500&recursion=1&web=1`）。早期调研整理的 `word/category/start/limit` 参数不正确，已修正。

**文件类型 category 代码**（百度网盘分类）：

| category | 类型 |
|:---:|------|
| 1 | 视频 |
| 2 | 音频 |
| 3 | 图片 |
| 4 | 文档 |
| 5 | 应用 |
| 6 | 其他 |
| 7 | 种子 |

> category 映射已对照 BoxPlayer `filecmd.ts`（`mapCategory`：1=video 2=audio 3=image 4=doc 5=app 7=bt，其余 default=other）核实。

**`list` 响应关键字段**（`list[]` 数组每项）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `fs_id` | int64 | **文件全局唯一 ID（跨重命名/移动稳定）** |
| `path` | string | 文件绝对路径（如 `/音乐/周杰伦/晴天.mp3`） |
| `server_filename` | string | 文件名（含扩展名） |
| `isdir` | int | 0=文件, 1=目录 |
| `size` | int64 | 文件大小（字节） |
| `category` | int | 文件类型代码（见上表） |
| `md5` | string | 云端哈希（非文件真实 MD5） |
| `local_ctime` / `local_mtime` | int | 客户端创建/修改时间 |
| `server_ctime` / `server_mtime` | int | 服务端创建/修改时间 |
| `thumbs` | object | 缩略图（`web=1` 时返回），结构为 `{url1, url2, url3, icon?}`，取 `url2 ?? url1 ?? url3` |
| `has_more` | int | 分页标志（仅在响应顶层，=1 时继续翻页 `start += limit`） |

> `list` 响应不直接含 `duration/bitrate`——这两个字段需 `filemetas` 且传 `needmedia=1` 才返回（见 §3.3）。

**`filemetas` 补充字段**（对照 BoxPlayer `filecmd.ts` 的 `BaiduFileMetaItem`）：
- **`media_info`**（传 `needmedia=1` 返回）：`{duration, duration_ms, channels, sample_rate, file_size, frame_rate, width, height, meta_info}`——其中 **`duration_ms` 是毫秒精度时长**，比顶层 `duration`（秒）更适合填 `Song.durationMs`
- **`thumbs`**：`{icon, url1, url2, url3, url4}`——`url2` 优先
- 响应容器兼容：`data.list || data.info`（两种结构都处理）
- 顶层 `duration`（秒）仍有，但优先 `media_info?.duration || duration`

**搜索示例**：
```
GET /rest/2.0/xpan/file?method=search
    &access_token={TOKEN}
    &key=周杰伦          ← 参数名是 key（非 word）
    &dir=/
    &num=500            ← 单页数量（BoxPlayer 用 500）
    &recursion=1        ← 递归全盘
    &web=1              ← 返回缩略图
```

### 3.3 文件串流（dlink 下载链接）

百度网盘**不提供原始文件直链**，串流分两步：

**Step 1：用 fs_id 换 dlink**
```
GET /rest/2.0/xpan/multimedia?method=filemetas
    &access_token={TOKEN}
    &fsids=[{fs_id}]
    &dlink=1              ← 必须传，否则不返回 dlink
    &thumb=1              ← 顺带拿缩略图
    &extra=1              ← 额外元数据
    &needmedia=1          ← 返回 media_info（时长毫秒精度等）
    &detail=1

响应：
{
  "list": [{
    "fs_id": 123456789,
    "dlink": "https://d.pcs.baidu.com/file/xxxxx...",  ← 下载直链，有效期短
    "filename": "晴天.mp3",
    "size": 4321024,
    "duration": 269,              ← 秒（顶层）
    "thumbs": { "icon": "...", "url1": "...", "url2": "..." },  ← thumb=1
    "media_info": {               ← needmedia=1 时返回
      "duration": 269,
      "duration_ms": 269123,      ← 毫秒精度，填 Song.durationMs 首选
      "channels": 2,
      "sample_rate": 44100,
      "file_size": "4321024"
    }
  }]
}
补偿说明：
- 响应容器兼容：`data.list || data.info`（两种结构都解析）
- `bitrate` 不保证稳定返回，优先用 `media_info` + 本地估算
```

> ⚠️ **dlink 可能不含 access_token**（BoxPlayer `adapter.ts:46` 实测）：拿到 dlink 后需检查 URL query 是否含 `access_token=`，若没有则手动拼上 `&access_token={TOKEN}`，否则请求 401/403。拼法：`url += (url.includes('?') ? '&' : '?') + 'access_token=' + encodeURIComponent(token)`。

**Step 2：GET dlink 拉取文件/串流**

> ⚠️ **关键约束**：dlink 请求**必须带 `User-Agent: pan.baidu.com` 请求头**，否则 >20MB 的文件会返回 403（百度反盗链机制）。这是 ExoPlayer 直接播放 dlink 的最大坑。BoxPlayer `adapter.ts:53-56` 还额外带了 **`Referer: https://pan.baidu.com/`**（双保险）。

```
GET {dlink}
Headers:
  User-Agent: pan.baidu.com          ← 必须！
  Referer: https://pan.baidu.com/    ← BoxPlayer 实证建议加（双保险）

特性：
- 支持 HTTP Range（可 seek，ExoPlayer progressive 流可用）
- dlink 有效期短（小时级），过期后需重新 Step 1 换取
- 非 VIP 用户有**下载限速**（约 100-200 KB/s），影响 seek 体验
```

**ExoPlayer 接入**：需自定义 `OkHttpDataSource` / `DefaultHttpDataSource`，在 `setUserAgent()` 恒定 `pan.baidu.com`。当前项目 OkHttp client（各适配器共用）需为百度源单独配置带此 UA 的 `OkHttpClient`，或通过 `DataSource.Factory` 注入。

**替代方案：M3U8 HLS 流**（`pcs.baidu.com/rest/2.0/pcs/file?method=streaming&type=M3U8_AUTO_720`）：
- 仅适用于**视频**（MV），音频文件无 M3U8 流
- 自适应码率，ExoPlayer 原生支持 HLS
- 但转码后的音质非原始，不适合 HiFi 音乐播放
- **结论：音乐用 dlink 原始流，MV 可用 M3U8**

### 3.4 已知约束汇总

| 约束 | 影响 | 对策 |
|------|------|------|
| dlink 有效期短（小时级，实测约 8h） | 缓存 URL 中途失效 | 缓存 TTL 保持全局 5min（`PLAY_URL_CACHE_TTL_MS`，见 §11 问题 6），远小于 dlink 有效期，方向安全；长时间播放后切回旧曲若 dlink 已过期，靠"播放失败清缓存重解析一次"兜底 |
| `User-Agent: pan.baidu.com` 必需（+ `Referer: https://pan.baidu.com/` 双保险） | ExoPlayer 默认 UA 会被 403 | 自定义 `DataSource.Factory` 恒设此 UA（见 §6.3.1 NeriPlayer 模式） |
| 非 VIP 下载限速 | seek 卡顿，首播慢 | UI 提示"网盘限速，缓冲中…"；不解决（百度商业策略） |
| 应用需审核 | 生产环境需百度审核通过 | 开发期可用测试模式（配额受限）；上线前提交审核 |
| QPS 限制 | 高频 API 调用被限流 | 文件索引本地缓存（见 §6.2）+ 扫描节流（对照 BoxPlayer `musicScanner.ts`：目录间 60ms 节流 + RateLimiter 分页限速） |
| API 错误码 | -111/-118 等需分别处理 | 统一错误码映射表，token 过期自动 refresh（并发刷新加锁，对照 BoxPlayer `withTokenRefreshLock`） |

### 5.1 关键设计决策

1. **百度网盘作为 `NetworkMusicService` 而非 `BackendAdapter`**：dlink 8h 过期 + 扁平文件系统 + OAuth 鉴权，三者均不符合 `BackendAdapter` 的"同步 getStreamUrl + 专辑结构 + 用户名密码"假设。走网络音乐路径零侵入主架构。

2. **本地 MV 优先于在线 Bilibili MV**：`MvSearchManager.services` 列表中 `BaiduMvFileService` 排在 `BilibiliMvService` 之前。当当前歌曲是百度歌曲时，先查网盘本地 MV 文件（用户自己保存的高质量 MV），未命中再 fallback 到 Bilibili 在线。

3. **流式串流而非下载后播放**：百度 dlink 支持 HTTP Range，ExoPlayer 可作为 progressive 流直接播放（配自定义 UA 的 DataSource）。大文件（FLAC 24bit/96kHz 可达 100MB+）不下载到本地，节省 TV 存储。

4. **文件索引本地缓存**：网盘 `listall` 一次请求可耗时长（大曲库数千文件），首次扫描后建本地索引（Room 或 JSON），后续浏览走索引 + 增量更新。避免每次进百度音乐 Tab 都等 10 秒。

#### 6.1.2 `BaiduOAuthClient` 设计（设备码模式为主，授权码 QR 码为备选）

```kotlin
class BaiduOAuthClient(
    private val client: OkHttpClient,
    private val prefs: AppPreferences
) {
    companion object {
        const val DEVICE_CODE_URL = "https://openapi.baidu.com/oauth/2.0/device/code"  // v2 修正：设备码专用端点（非 token 端点）
        const val TOKEN_URL = "https://openapi.baidu.com/oauth/2.0/token"
        // 从 BuildConfig 读取（值来自 keystore.properties，不硬编码在源码中）
        val DEFAULT_APP_KEY: String get() = BuildConfig.BAIDU_APP_ID
        val DEFAULT_SECRET_KEY: String get() = BuildConfig.BAIDU_APP_SECRET
        const val SCOPE = "basic,netdisk"
        const val DEVICE_CODE_EXPIRE_SEC = 300   // 设备码有效期 5 分钟
        const val POLL_INTERVAL_MS = 5000         // 默认轮询间隔 5 秒
    }

    // ── 设备码模式（TV 首选）──

    /** 请求设备码（电视显示短码，用户手机访问 verification_url 输入） */
    suspend fun requestDeviceCode(): DeviceCodeResult? = withContext(Dispatchers.IO) {
        val appKey = prefs.getBaiduAppKeySync() ?: DEFAULT_APP_KEY
        val secretKey = prefs.getBaiduSecretKeySync() ?: DEFAULT_SECRET_KEY
```

**总开关语义**（关键设计）：
- **关闭**：app 完全不访问该网盘--不刷新 token、不调任何 API、不建/不刷新索引、`NetworkMusicManager.services` 中不注册该源的 service。对 app 而言该网盘源不存在。
- **开启**：按登录状态决定后续--未登录则引导扫码；已登录则激活 service + 后台索引刷新。

```kotlin
object BaiduFilenameParser {
    private val BRACKETS_RE = Regex("""[\(\[（【][^\)\]）】]*[\)\]）】]""")
    private val TRAILING_TAGS_RE = Regex("""\s*-\s*(official|mv|hd|hq|lossless|live|remix|cover|伴奏|纯音乐|高清|无损|完整版|live现场)\s*$""", RegexOption.IGNORE_CASE)
    private val SEPARATORS = listOf(" - ", "_-_", "－", "-", " – ", "–")

    private fun clean(s: String): String =
        s.replace(BRACKETS_RE, " ")
            .replace(TRAILING_TAGS_RE, " ")
            .replace(Regex("""[_\.]+"""), " ")
            .replace(Regex("""\s+"""), " ")
            .trim()

    private fun stripTrackNo(s: String): String =
        s.replace(Regex("""^\s*(?:cd\s*\d+\s*)?\d{1,3}\s+[-–—]?\s*""", RegexOption.IGNORE_CASE), "").trim()

    fun parse(filename: String): Pair<String, String> {
        val base = stripTrackNo(clean(filename.substringBeforeLast('.')))
        for (sep in SEPARATORS) {
            val i = base.indexOf(sep)
            if (i > 0) {
                val artist = stripTrackNo(base.substring(0, i).trim())
                val title = stripTrackNo(base.substring(i + sep.length).trim())
                if (artist.isNotBlank() && title.isNotBlank()) return artist to title
            }
        }
        return "" to base
    }
}
```

**索引策略**：
- **所有权（v2 明确）**：`BaiduFileIndexCache` 实例由 `BaiduNetdiskService` 构造注入持有，`AppPreferences` 只存配置（`rootDir`/`enabled` 等）不存索引——§6.3.2 的 search 从该实例读取
- 首次进入百度音乐 Tab：触发全量扫描（主路径：BFS 逐目录 `list` + 60ms 节流，见下方"扫描节流"；`listall` 单请求方案未验证，实测通过后可作可选加速），写入索引（后台协程，UI 显示进度）
- 后续进入：先读索引即时展示，后台 `listAllAudio` 增量更新（对比 `server_mtime`）
- 搜索：先查本地索引（毫秒级），命中即返回；未命中或索引过期（>1 天）走百度 `search` API（`key` 参数）
- 文件被用户在网盘端删除/重命名：下次增量扫描时同步（`fs_id` 稳定，`path` 变了跟着更新）

**扫描节流与音频判定**（对照 BoxPlayer `musicScanner.ts` 实证）：
- **BFS 扫描 + 节流**：目录逐层 BFS（深度上限 8），每目录之间 60ms 节流（`FOLDER_THROTTLE_MS`），分页请求走 RateLimiter 限速——避免触发百度 QPS 限流。大曲库首次扫描慢可接受，节流保命。
- **音频文件判定双判据**：`category == 2`（百度音频分类）**或**扩展名在音频白名单内。BoxPlayer 的 30 个音频扩展名清单：
  ```
  .mp3 .flac .wav .ape .ogg .aac .aif .aiff .cda .dsf .dts .dtshd .eac3
  .m1a .m2a .m4a .m4b .m4r .mka .mpa .mpc .opus .ra .tak .tta .wma .wv
  .amr .ac3 .au
  ```
  注意 `.ape/.dsf/.dts/.tak/.tta/.wv` 等无损格式 ExoPlayer 原生不支持，判定为音频但播放可能失败——UI 需容错提示"该格式设备不支持"。

**手动重建索引**（设置页操作入口）：

用户在设置页"百度网盘"子项内可执行手动重建索引，触发时机：首次登录后、切换音乐根目录后、怀疑索引与网盘不一致时。

- **入口位置**：设置页 → 网盘 → 百度网盘（展开） → 音乐根目录下方，显示"**索引状态**"行：
  ```
  索引状态：已扫描 1,284 首（2026-08-20 15:30）
  [ 重建索引 ]
  ```
- **点击"重建索引"** → 弹出确认框（"重新扫描百度网盘音乐目录，将清空现有索引并重新扫描，请确保网络畅通。确认？"）
- **确认后**：清空 `BaiduFileIndexCache`（`clear()`），设置 `BaiduFileIndex.lastSyncAt = 0`，触发全量 `listAllAudio(root)` 扫描（BFS + 节流，同 §6.2.3 所述策略）
- **扫描进度**：在设置页该行位置显示实时进度条 + 计数（"正在扫描第 47/1,500 个文件…"），扫描完成后进度条消失，更新索引状态时间和计数
- **失败处理**：扫描中途失败（网络/限流/超时）→ 保留已扫描到的部分索引（不丢弃），显示"扫描中断（已扫描 N 首），可再次重建"

#### 6.3.1 音乐串流 `BaiduStreamFactory`

```kotlin
/**
 * 百度网盘音频 DataSource 工厂
 *
 * 关键：恒设 User-Agent: pan.baidu.com + Referer: https://pan.baidu.com/
 *      （BoxPlayer adapter.ts 实证双头必需）
 * 支持 HTTP Range（seek）
 */
class BaiduStreamFactory(
    private val api: BaiduPanApi,
    private val oauth: BaiduOAuthClient
) {
    companion object {
        const val BAIDU_UA = "pan.baidu.com"
        const val BAIDU_REFERER = "https://pan.baidu.com/"
        const val DLINK_HOST_MARKERS = listOf("d.pcs.baidu.com", "pan.baidu.com")

        /** 判断 URL 是否为百度 dlink 域名（v2：移入 companion，供 DataSource 拦截器静态调用） */
        fun shouldInject(url: String?): Boolean =
            url?.let { u -> DLINK_HOST_MARKERS.any { u.contains(it) } } == true
    }

    /**
     * 解析播放 URL：fs_id -> filemetas(dlink) -> 返回带 access_token 的 dlink
     * dlink 有效期短（小时级），但缓存走 NetworkMusicManager 全局 5min TTL（§11 问题 6），此处不做缓存决策
     */
    suspend fun resolveStreamUrl(fsId: Long): String? = withContext(Dispatchers.IO) {
        val metas = api.fileMetas(listOf(fsId))
        val dlink = metas.firstOrNull()?.dlink ?: return@withContext null
        // ⚠️ dlink 可能不含 access_token，需手动补（BoxPlayer adapter.ts:46 实证）
        val token = oauth.getValidAccessToken() ?: return@withContext null
        if (!dlink.contains("access_token=")) {
            dlink + (if (dlink.contains('?')) "&" else "?") + "access_token=" + URLEncoder.encode(token, "UTF-8")
        } else dlink
    }
}
```

> **接入点（对照 NeriPlayer 实现）**：不要"为百度源单独建 DataSource.Factory"。参照 NeriPlayer `ConditionalHttpDataSourceFactory.kt` 的 `transformDataSpec` 模式：写一个 `BaiduConditionalHttpDataSource`，包装现有 `OkHttpDataSource.Factory`，在 `open(DataSpec)` 时按 `dataSpec.uri` 判断 `shouldInject()`（域名含 `d.pcs.baidu.com`/`pan.baidu.com`），命中则 `dataSpec.buildUpon().setHttpRequestHeaders(headers + UA + Referer).build()`，未命中原样透传。这样 NAS 歌曲（jellyfin/navidrome 域名）、Meting 流量、百度 dlink 共用一个 DataSource 链路，按域名自动区分注入头，无需为百度源切换整个 Factory。
>

### 6.5 MV 文件搜索与歌曲关联

#### 6.5.1 需求拆解

用户需求："搜索保存的 MV，与歌曲文件或歌曲唯一值关联"。

两个动作：
1. **搜索 MV**：在用户网盘中查找与当前歌曲匹配的视频文件（.mp4/.mkv 等）
2. **关联**：将找到的 MV 与歌曲绑定，下次播该歌曲直接用此 MV

#### 6.5.2 关联策略

| 策略 | 匹配规则 | 适用场景 |
|------|---------|---------|
| **A. 同目录同名** | MV 与歌曲在**同一目录**，文件名去扩展名**相同**（如 `晴天.mp3` ↔ `晴天.mp4`） | 最精确，零误匹配，用户将 MV 与音乐文件放在一起即可 |
| **B. 歌手+歌名搜索** | 用歌曲的 `title` 和 `artist` 作为关键词，在**MV 路径**（或音乐根目录）下搜索视频文件（`category=1`） | 歌手名+歌名组合基本唯一，误匹配概率低，且不依赖目录结构 |
| **C. 手动指定** | 用户在歌曲详情页手动选一个 MV 文件绑定 | 兜底，精确但繁琐 |

> **"同目录同名"的目录名是指**：音乐文件所在的父目录。如果 MV 文件与音乐文件在同一个文件夹且文件名相同（仅扩展名不同），自动匹配，零配置。

**MV 路径设置**：在设置页"百度网盘"子项新增**可选**的"MV 路径"输入（浏览选择），用户可独立指定 MV 文件所在的网盘目录。未设置时默认与音乐根目录相同（`/音乐`）；如果用户既未设置 MV 路径也未设置音乐根目录（保持默认），则**不搜索百度本地 MV**（仅使用 Bilibili 在线 MV）。

**推荐组合**：A（同目录同名，优先）→ B（歌手+歌名搜索，限定在 MV 路径内）→ C（手动指定，兜底）。**不开启全局模糊搜索**（名称相似度匹配容易误匹配，如"告白气球"可能匹配到多个视频）。结果写入 `MvPersistentCache`（复用现有 `Map<songId, MvCacheEntry>` 机制）。

**§6.1.3 设置页 UI 更新**：百度网盘子项内新增"MV 路径"行，点击浏览选择，未填时显示"与音乐根目录相同"。

#### 6.5.3 `BaiduMvFileService` 实现 `MvSearchService`

> **接口变更（v2 评审补充，关键）**：现有 `MvSearchService.searchMv(title, artist, excludeBvids, minSimilarity)` **只传标题与艺术家**——`BaiduMvFileService` 判断"仅百度歌曲生效"需要 `song.networkSource`，"同目录同名匹配"需要 `song.id` 反查 path，二者都拿不到。方案：接口新增**带默认值的 `song` 参数**，`BilibiliMvService` 及既有调用零改动：
>
> ```kotlin
> interface MvSearchService {
>     suspend fun searchMv(
>         title: String,
>         artist: String,
>         excludeBvids: Set<String> = emptySet(),
>         minSimilarity: Float = 0.5f,
>         song: Song? = null          // 新增：完整歌曲上下文（判源 / 反查 path 用）
>     ): MvSearchResult?
>
>     suspend fun resolveMv(bvid: String): MvInfo?
> }
> ```
>
> `MvSearchManager.searchMvFor` 把 `song` 透传给各 service；非百度歌曲传到 `BaiduMvFileService` 时直接返回 null（等同跳过）。已列入 Phase 6 步骤 30。

```kotlin
class BaiduMvFileService(
    private val api: BaiduPanApi,
    private val oauth: BaiduOAuthClient,
    private val streamFactory: BaiduStreamFactory,
    private val indexCache: BaiduFileIndexCache,   // v2：从索引反查 path（§6.2.3 所有权），替代 v1 的 prefs.getBaiduSongPathByFsId
    private val prefs: AppPreferences
) : MvSearchService {

    override val sourceId = "baidu-mv-file"

    /**
     * 为歌曲搜索匹配的网盘 MV 文件
     * 策略：同目录同名 → 歌手+歌名搜索（限定 MV 路径内）→ 手动指定（兜底）
     * 不开全局模糊搜索（避免误匹配）
     */
    override suspend fun searchMv(
        title: String,
        artist: String,
        excludeBvids: Set<String>,
        minSimilarity: Float,
        song: Song?                    // 接口新增参数（见上方"接口变更"）
    ): MvSearchResult? = withContext(Dispatchers.IO) {
        // 仅对百度歌曲生效（song 上下文由新增接口参数传入）
        if (song?.networkSource != "baidu") return@withContext null

        // 获取 MV 搜索路径：未设置时默认与音乐根目录相同；音乐根目录也未设置时不搜索
        val mvDir = prefs.getBaiduMvDirSync() ?: prefs.baiduMusicRootDirSync() ?: return@withContext null

        // 1. 同目录同名：MV 与歌曲在同一目录，文件名去扩展名相同
        val songPath = indexCache.getPathByFsId(song.networkId?.toLongOrNull())
        songPath?.let { findMvInSameDir(it) }?.let { return@withContext buildResult(it, title, artist) }

        // 2. 歌手+歌名搜索：在 MV 路径内搜索视频文件
        val keywords = listOfNotNull(
            title.takeIf { it.isNotBlank() },
            artist.takeIf { it.isNotBlank() }
        ).joinToString(" ")
        if (keywords.isNotBlank()) {
            val candidates = api.searchVideo(keywords, dir = mvDir)
            val best = candidates.firstOrNull { /* 按标题匹配度排序，取第一个 */ }
            if (best != null) return@withContext buildResult(best, title, artist)
        }

        null  // 未命中，MvSearchManager fallback 到 BilibiliMvService
    }

    /** 解析 MV 直链（dlink，8h 有效，用 M3U8 或原始流） */
    override suspend fun resolveMv(bvid: String): MvInfo? {
        // bvid 实际是 "ntwk_baidu_mv_${fsId}"，解析出 fsId
        val fsId = bvid.removePrefix("ntwk_baidu_mv_").toLongOrNull() ?: return null
        val metas = api.fileMetas(listOf(fsId))
        val meta = metas.firstOrNull() ?: return null

        // 视频可用 M3U8 HLS 流（自适应码率），或直接用 dlink progressive
        val videoUrl = meta.dlink ?: return null  // v2：dlink 可空（§7.1 统一模型），缺失时放弃
        return MvInfo(
            bvid = bvid,
            title = meta.filename,
            coverUrl = meta.thumbs?.url,  // 视频缩略图
            videoUrl = videoUrl,
            durationMs = meta.duration,   // v2：§7.1 统一后 duration 已是毫秒（durationMs 优先），勿再 ×1000
            fetchedAt = System.currentTimeMillis()
        )
    }

    private suspend fun findMvInSameDir(songPath: String): BaiduFile? {   // v2：suspend（调用挂起函数 listDir）
        val parentDir = songPath.substringBeforeLast('/')
        val basename = songPath.substringAfterLast('/').substringBeforeLast('.')
        val dirFiles = api.listDir(parentDir)
        return dirFiles.files.find {
            !it.isDir && it.category == CATEGORY_VIDEO &&
                it.serverFilename.substringBeforeLast('.') == basename
        }
    }
}
```

#### 6.5.4 接入 `MvSearchManager`

`NasMusicApp.onCreate` 构造 `MvSearchManager` 时，`services` 列表顺序：

```kotlin
val mvServices = listOf(
    BaiduMvFileService(...),      // 本地 MV 优先
    BilibiliMvService(...)        // 在线 Bilibili fallback
)
val mvSearchManager = MvSearchManager(
    services = mvServices,
    cacheTtlMs = 45 * 60 * 1000L,
    persistentCache = MvPersistentCache(this)
)
```

`MainViewModel.triggerMvSearch(song)` 判断：
- 若 `song.networkSource == "baidu"`：先查 `BaiduMvFileService`，未命中再 `BilibiliMvService`
- 若 `song.networkSource != "baidu"`：跳过 `BaiduMvFileService`，直接 `BilibiliMvService`

> `MvPersistentCache` 的 `MvCacheEntry.bvid` 字段语义泛化：存 `"ntwk_baidu_mv_${mv_fs_id}"`（百度 MV）或 B 站 bvid。`resolveMv(bvid)` 按 `bvid` 前缀路由到对应 service。**需小幅修改 `MvPersistentCache` 或在 `MvSearchManager` 加 bvid 前缀路由逻辑**。
>
> **现有行为差异（v2 评审补充，源码核实）**：
> - `MvSearchManager` 内存缓存 key 是 `title|artist`（`buildCacheKey`，非 song.id）——同名同歌手的 NAS 歌与百度歌共享缓存结果，语义可接受（均为 B 站搜索结果），不改
> - `MvSearchManager.resolveMv(bvid)` 轮询**所有** service：B 站 service 会收到 `ntwk_baidu_mv_*` 前缀的 bvid，依赖"`resolveMv` 对无法解析的 bvid 优雅返回 null"这一既有契约（BilibiliMvService 现状即如此），百度 bvid 自然落到 BaiduMvFileService 解析
> - 持久缓存命中路径（`persistentCache.get(song.id) → resolveMv(entry.bvid)`）依赖 services 列表中 BaiduMvFileService 排前（与上方注册顺序一致）；即使排后，百度 bvid 先打到 B 站 service 返回 null 后仍会轮询到百度，仅多一次无效调用，可接受

#### 6.5.5 MV 播放（复用现有 `MvPlaybackScreen`）——搜索调度与切换逻辑

**搜索调度链路**（`MvSearchManager.searchMvFor(song)` 完整流程）：

```
用户切歌/播放
  └─ MainViewModel.triggerMvSearch(song)
      └─ MvSearchManager.searchMvFor(song)
          │
          ├─ [song.networkSource == "baidu"]:
          │   ├─ ① BaiduMvFileService（优先：同目录同名 → 歌手+歌名搜索，限定 MV 路径内）
          │   │   ├─ 命中 → 返回 MvSearchResult(source="baidu", mv, alternatives)
          │   │   └─ 未命中 → 继续
          │   └─ ② BilibiliMvService（fallback：在线 B 站搜索）
          │       ├─ 命中 → 返回 MvSearchResult(source="bilibili", mv, alternatives)
          │       └─ 未命中 → 返回 null（MTV 按钮置暗）
          │
          └─ [song.networkSource != "baidu"]:
              └─ ① BilibiliMvService（仅此一路，跳过 BaiduMvFileService）
                  ├─ 命中 → 返回 MvSearchResult(source="bilibili", ...)
                  └─ 未命中 → 返回 null
```

**两个来源互不混合，按优先级串联**：

| 维度 | 百度网盘本地 MV | Bilibili 在线 MV |
|------|----------------|-----------------|
| 来源 | `BaiduMvFileService`（同目录同名 → 歌手+歌名搜索，限定 MV 路径内） | `BilibiliMvService`（B 站 API 搜索） |
| 适用歌曲 | 仅 `song.networkSource == "baidu"` 的歌曲 | 所有歌曲（百度歌曲的 fallback） |
| 文件位置 | 用户百度网盘内的视频文件（.mp4/.mkv 等） | B 站服务器 |
| 画质/音质 | 用户自己保存的原始文件，质量由用户决定 | 免登录受限（≤540p/720p） |
| 唯一标识 | `ntwk_baidu_mv_${mv_fs_id}` | B 站 `bvid` |
| 持久缓存 | `MvPersistentCache` 按 `song.id` 存 `ntwk_baidu_mv_${fs_id}` | `MvPersistentCache` 按 `song.id` 存 `bvid` |

> **两个来源不混合**：一个 `MvSearchResult` 的 `mv` 和 `alternatives` 均来自同一服务。不存在"百度 MV 为主播，B 站 MV 放 alternatives"的设计——因为来源不同、刷新机制不同（百度 dlink 需自己补 access_token，B 站需 resolveMv 三步取流），混合后 `MvPlaybackScreen` 要同时处理两种刷新逻辑，复杂度上升不可接受。**替代方案**：如果 `BaiduMvFileService` 和 `BilibiliMvService` 都返回了结果，则 `MvSearchManager` 只返回 `BaiduMvFileService` 的结果（本地优先），用户如需切到 B 站版本，可在 `MvPlaybackScreen` 点击"搜 B 站"按钮单独触发一次 Bilibili 搜索（见下文切换逻辑）。

**`MvPlaybackScreen` 切换逻辑**：

```
MvPlaybackScreen 打开时
  │
  ├─ 显示来源标签："网盘 MV" 或 "B站 MV"
  ├─ 自动播放 primary MV
  │
  ├─ 用户点击"切换"按钮（当 alternatives.size > 0 时）：

  │   ├─ [当前来源 == "baidu"]:
  │   │   ├─ 循环切换 alternatives（同来源的其他文件名匹配候选，如"歌名-完整版.mp4"→"歌名-官方MV.mp4"）
  │   │   └─ 若 alternatives 全部切完，显示"搜 B 站"按钮（触发 BilibiliMvService 搜索，结果作为新 alternatives 追加）
  │   │
  │   └─ [当前来源 == "bilibili"]:
  │       └─ 循环切换 alternatives（B 站的其他搜索结果）
  │
  └─ 用户点击"搜 B 站"按钮（仅 Baidu 歌曲且 Baidu 已搜到 MV 时出现）：
      └─ 触发 BilibiliMvService 搜索 → 若命中，将 B 站结果作为新候选加入交替列表，切换时从"网盘 MV"→"B站 MV"
```

**切换按钮 UI**：

```
┌─────────────────────────────────────┐
│  [⏮]  [⏸/▶]  [⏭]  [🎬 切换(1/3)]  [📄 歌词]   │
│                    ↑ 来源标签：网盘 MV           │
└─────────────────────────────────────┘
```

- 按钮显示当前候选序号和总数（如 `切换(1/3)`），点击切换
- 来源标签在 `MvInfo` 的 `source` 字段，渲染在按钮旁或上方
- 仅 `alternatives.size > 0` 时按钮可点击，否则灰显

**dlink 播放细节**：

百度 MV 的 dlink 同样需要 `User-Agent: pan.baidu.com` + `Referer: https://pan.baidu.com/` + 手动补 `access_token`。`MvPlaybackScreen` 的第二个 ExoPlayer 使用 `BaiduHttpDataSourceFactory`（§6.3.1 的 `transformDataSpec` 拦截器方案），按 URL 域名自动注入百度头——B 站 MV 的播放 URL 不命中 `d.pcs.baidu.com` 域名，自然不会被拦截，两者共用同一个 DataSource Factory 零冲突。

## 九、风险与限制

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| **dlink 8h 过期** | 缓存 URL 中途失效，播放报错 | 缓存 TTL 保持全局 5min（`PLAY_URL_CACHE_TTL_MS`，§11 问题 6），远小于 dlink 有效期；长时间播放后切回旧曲若已过期，"播放失败清缓存重解析一次"兜底 |
| **`User-Agent: pan.baidu.com` 必需** | ExoPlayer/Coil 默认 UA 被 403 | 自定义 DataSource.Factory + Coil OkHttpClient 恒设此 UA |
| **非 VIP 下载限速** | seek 卡顿，首播慢 | UI 缓冲提示；不解决（百度商业策略） |
| **应用需百度审核** | 上线前需通过 | 开发期测试模式；上线前提交审核 |
| **client_secret 嵌入开源 App** | 可被提取滥用 | 支持用户自填 AppKey/Secret 覆盖；文档说明风险 |
| **fs_id 文件被删** | 歌单条目失效 | 播放失败提示"文件已不存在"；自动从歌单移除或标记失效 |
| **大曲库 listall 慢** | 首次扫描 10s+ | 本地索引 + 增量更新；UI 显示扫描进度 |
| **内嵌 ID3 解析兼容性** | 部分文件 ID3v2 帧格式非标 | 轻量解析器容错；解析失败 fallback 到网络匹配 |
| **M3U8 仅视频** | 音频无法用 HLS | 音频用 dlink progressive 流（支持 Range seek） |
| **百度 API 升级/不兼容**（无显式版本号，静默演进） | 端点/参数/字段变更导致功能异常 | §3.0 版本追踪机制：集中常量表 + 启动版本探测 + 响应解析容错 + 错误码映射；变更后核对官方文档 → 更新常量表 → 回填 §3.0 基线表 → 发版 |
| **设备码轮询中断** | 用户授权过程中 TV 网络中断或抛出异常 | 轮询超时处理；超时后显示"请重新登录"按钮，引导用户重新发起设备码请求 |

## 十一、待评审问题

1. **AppKey/SecretKey 策略**：设备码模式仍需 `client_id`（AppKey）和 `client_secret`（SecretKey）——设备码请求和 token 轮询/刷新均需要。**已从 BoxPlayer 源码找到答案**：`src/utils/baidu.ts:4` 从 `secrets.generated` 导入 `BAIDU_APP_ID`/`BAIDU_APP_SECRET`，编译在发行版中，用户不需要自己注册。嵌入式方案是通行做法。建议：默认嵌入自有 AppKey（上线前在百度开放平台注册），同时保留设置页"自填 AppKey/SecretKey"功能供有顾虑的用户覆盖。
2. **扫码授权回调**：`redirect_uri=oob` 时，用户手机扫码授权后，手机浏览器页面会显示**"授权码为:xxxxxxxx"**（32 位字母数字），用户需手动从手机抄到电视上用 D-Pad 输入，体验极差。方案 B（TV 端 HTTP 服务接收回调）也有问题：百度要求 `redirect_uri` 必须在控制台**预注册域名**，电视的局域网 IP 是动态的，无法预注册，HTTP 回调方案不可行。

   **推荐方案 C：设备码模式（Device Code）**——这是百度开放平台专为**弱输入设备**（电视、手表等）设计的授权模式：
   - 电视调用 `GET https://openapi.baidu.com/oauth/2.0/device/code?response_type=device_code&client_id=...&scope=basic,netdisk` 获取一个**短设备码**（如 `ABCD-1234`，4-8 位字母数字；此步无需 client_secret，v2 修正端点）
   - 电视在屏幕上显示设备码和链接 `https://openapi.baidu.com/device`
   - 用户用手机访问该链接，输入设备码，完成授权
   - 电视轮询 token 端点（`grant_type=device_token`+`device_code`），拿到 `access_token`（可刷新）
   - **不需要 `redirect_uri`**，不需要手动输入长 code，`client_secret` 仍需要（与 QR 码方案一致），`Access Token` 过期后可刷新。
   - 已有 Go 开源 SDK 实现验证（`baowuhe/go-bdisk`、`lfhy/xpan` 均支持 device code 流程）

   **结论：采用设备码模式为 TV 首选授权方案。** 原 §6.1 的授权码 + QR 码设计需改为设备码模式（见下文更新）。
3. **音乐根目录默认值**：**已确认默认 `/音乐`**，直到用户手动浏览选择后覆盖。首次进入设置页时预填充 `/音乐`，用户未设置前索引扫描范围即为 `/音乐` 及其子目录。
4. **MV 匹配默认策略**：**已确认**：同目录同名优先（MV 与歌曲在同一目录，文件名去扩展名相同）→ 歌手+歌名关键词搜索（限定在 MV 路径内）→ 手动指定（兜底）。**MV 路径**在设置页可选配置，未填写时默认与音乐根目录相同（`/音乐`）；音乐根目录也未设置时（保持默认 `/音乐` 且未手动选择），MV 路径自动与音乐根目录一致。**不开全局模糊搜索**（避免误匹配）。
5. **内嵌 ID3 解析依赖**：**已确认自写轻量解析器**（~100 行，仅解析 ID3v2.3/2.4 的 USLT 和 APIC 帧）。不引入 `jaudiotagger-android` 重型依赖。边角格式（非标准 ID3v2 帧、编码异常等）不支持的场景，歌词/封面 fallback 到网络匹配（§6.3.3/§6.3.4），不影响核心播放。
6. **dlink 缓存 TTL**：**已确认保持 5 分钟**，不单独为百度源放宽。理由：dlink 按需解析（首次播放才拿缓存），5 分钟内重播同一首歌极少发生；7 小时 TTL 在 dlink 有效期缩短时有播放失败风险；零代码改动，复用现有 `NetworkMusicManager.playUrlCache`。
7. **百度网盘是否作为独立 Tab**：**已确认独立网盘 Tab（`Screen.Netdisk`）**，不并入现有 Network Tab。理由：网盘是"浏览优先"（目录树+文件列表），Network 是"搜索优先"（关键词+扁平结果），两种交互范式不可混用；未来阿里云盘/123 网盘都在此 Tab 下扩展，结构清晰。内部用子页面状态机管理（目录浏览/搜索/MV 选择等），不污染全局 `Screen` 枚举。
